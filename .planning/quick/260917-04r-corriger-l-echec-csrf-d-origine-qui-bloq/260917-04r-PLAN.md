<objective>
Reparer la connexion au navigateur, refusee en 403 par le controle d'origine du CSRF, et
fermer le trou de test qui a laisse la suite entierement verte au-dessus de ce refus.

**Le diagnostic est clos, il ne se refait pas.** `web/vite.config.ts` declare le proxy en
forme chaine (`"/api": "http://127.0.0.1:8010"`), forme pour laquelle Vite met
`changeOrigin: true` par defaut : le proxy reecrit l'en-tete `Host` en `127.0.0.1:8010`.
`CsrfViewMiddleware` reconstruit l'origine attendue depuis `request.get_host()`, la compare
a l'`Origin: http://localhost:5173` du navigateur, ne trouve aucune correspondance, et
`CSRF_TRUSTED_ORIGINS` n'existe ni dans `base.py` ni dans `local.py`. Refus exact capture :
`Origin checking failed - http://localhost:5173 does not match any trusted origins.`

Pourquoi 179 tests backend et 50 frontend sont verts pendant qu'un vrai navigateur est
refuse : **aucun test n'envoie d'en-tete `Origin`.** Django saute integralement le controle
d'origine quand l'en-tete est absent en HTTP simple, et la suite vitest double `fetch`. La
meme requete curl passe de 200 a 403 selon la seule presence de `-H "Origin: ..."`.

Purpose: un opticien ne peut pas se connecter en developpement, et la suite ne le dit pas.
Output: deux corrections (proxy + tolerance de developpement) et un test qui echoue si le
refus revient.

**Ordre impose — test d'abord.** Le test entre en premier et doit etre rouge sur un 403,
avant toute correction. Ce projet est test-first (`.planning/TESTING.md` section 1) : un test
ecrit apres la correction est ecrit pour passer.

Modele du test frere, `test_perm01_une_requete_api_sans_jeton_csrf_est_refusee` (ligne ~613) :
`api = _client_api(csrf=True)`, puis `api.get(CSRF)` (204, pose le cookie `csrftoken`), puis
les POST avec `headers={"x-csrftoken": api.cookies["csrftoken"].value}`.

`plateforme/comptes/views.py` :

```python
@method_decorator(csrf_protect, name="dispatch")
class VueConnexion(APIView):
    authentication_classes: list = []
    permission_classes = [AllowAny]
    throttle_scope = "connexion"   # DEFAULT_THROTTLE_RATES: {"connexion": "10/min"}
```

C'est ce `csrf_protect` qui declenche le controle d'origine sur un point de terminaison
anonyme — les vues DRF sont `csrf_exempt` au niveau du middleware, donc sans lui le controle
ne tournerait pas du tout. Contrat de statuts 03-08 : 200 succes, 400 echec d'identifiants,
403 CSRF, 429 limite, 503 affaire injoignable.

`config/settings/test.py` fait `from .base import *`, **jamais** de `local.py` :
`CSRF_TRUSTED_ORIGINS` est donc absent du run de tests, et le restera apres la correction.
C'est pour cela que le test lit la liste dans le module de reglages de developpement et
l'applique par `override_settings` — sinon il ne prouverait rien sur ce qui est livre.

`setup_test_environment()` ajoute `testserver` a `ALLOWED_HOSTS` : l'hote du client de test
est `testserver` et ne peut pas devenir `localhost:5173` sans override. C'est voulu ici —
l'hote doit differer de l'origine, exactement comme dans le defaut.

**Piege verifie dans le Django installe (6.1.x), a documenter dans la docstring.**
`csrf_protect = decorator_from_middleware(CsrfViewMiddleware)` et `make_middleware_decorator`
(`django/utils/decorators.py:126`) instancient le middleware **une seule fois, a l'import du
module de vues**. `allowed_origins_exact` et `csrf_trusted_origins_hosts` sont des
`cached_property` (`django/middleware/csrf.py:174-186`) et `django/test/signals.py` ne contient
**aucun** recepteur qui les invalide sur `setting_changed`. Consequence : la premiere requete
de la session qui porte un `Origin` ne correspondant pas a l'hote fige la liste pour tout le
processus. Donc :

- les deux jambes du test partagent **un seul** `override_settings`, jamais deux valeurs
  differentes — deux overrides donneraient silencieusement le meme resultat aux deux ;
- un futur test qui enverrait un `Origin` ne peut pas supposer que son propre override gagne.
  L'ecrire dans la docstring est la seule trace qui en restera.

`django/middleware/csrf.py:271 _origin_verified` : si `origin == request._current_scheme_host`
la requete est acceptee **avant** toute lecture de la liste de confiance. C'est exactement ce
que produit `changeOrigin: false` en developpement, et un reverse proxy qui preserve `Host` en
production.
