### 15.2 The one pre-existing gap Phase 4 must not repeat

`03.1/deferred-items.md` **D-1**: the shell's magasin selector trigger has **no accessible name** —
`combobox` is a *name-from-author* role, so its visible text never becomes its name.

**Contract for this phase:** every new `role="combobox"` carries an `aria-labelledby` pointing at a
**visible** `<label>`, and a named test asserts a non-empty `computeAccessibleName()` for each.
§25.2 lists them. Phase 4 does not fix D-1 — it is not this phase's file — but §28 keeps it on the
board.

### 15.3 Amendment — `react-hook-form` is deferred again, to Phase 6

`03` §1 wrote: *"`react-hook-form` → Phase 4 (first multi-field domain form)"*. **This document
overrules that, and the planner must know it is an overrule rather than an omission.**

Reasons, in order of weight:

1. **The validation model of this phase is three-tiered** — hard refusal, non-blocking warning,
   readback (§16). A warning is not an error, and it must not set `aria-invalid` (§16.4). Expressing
   "not an error but say something" through `setError` is a severity hack inside someone else's
   state machine.
2. **The clinical bounds come from the server** (§16.2). A resolver schema (`zod`, `yup`) would be a
   second written copy of numbers that D-4b says must live in exactly one named place. The owner has
   already changed those numbers once.
3. The ordonnance form is **one flat object of ~22 fields** with blur-time normalisation. A typed
   `useReducer` plus two pure modules (`normaliser.ts`, `verifier.ts`) is smaller, and — the real
   win — **the two pure modules are testable without rendering anything**, which matters because
   jsdom computes no CSS and a rendering test here proves less than a unit test.
4. Phase 3 shipped `Connexion` and `CreerCompte` as controlled components. Adding a form library now
   gives the codebase two idioms for its first three forms.

**Recorded counter-argument:** RHF reduces re-renders on large forms. At 22 fields on a desktop that
is not a measured problem, and nothing here is measured. **Revisit at Phase 6**, whose facture lines
are a dynamic field array — which is the case RHF actually wins.

Consequence: the shadcn `form` block is **not** installed in Phase 4.

### 15.4 Amendment — the date input ships without a calendar popover

`03` §8.2 last row: *"A masked text input `jj/mm/aaaa` plus a `popover` calendar. Phase 4 builds it."*

**Phase 4 builds the masked text input and not the calendar.** `type="date"` stays forbidden for the
reason §8.2 already gives.

- A `date de prescription` and a `date de naissance` are both **read off paper and typed**. A fast
  typist types `14/09/2026` in nine keystrokes; a calendar for a date three years in the past is four
  clicks and a month-by-month scroll.
- A calendar means `react-day-picker` + `date-fns` + a locale surface, in a product that pins its
  formats to a shared fixture precisely to keep locale data out of the decision path.

**This is a judgement call and it is a partial reversal of an inherited decision, so it is flagged:**
open question §28-Q3. If the developer wants the calendar, it is additive — the masked input stays
the primary control and the popover becomes a secondary trigger. Nothing else changes.

**The masked input, specified once, used by both dates:**

| Property | Value |
|---|---|
| Component | `ChampDate` in `web/src/format/` peer directory `web/src/champs/` |
| Markup | `<input type="text" inputmode="numeric" autocomplete="off">`, 36px, width 136px |
| Placeholder | `jj/mm/aaaa` — **and a real `<label>` above it**, never placeholder-as-label (`03` §10) |
| While typing | Slashes inserted after the 2nd and 4th digit. Nothing else is rewritten mid-keystroke |
| On blur | `14/9/26` → `14/09/2026`. A two-digit year ≤ today's year + 1 is 20xx, otherwise 19xx |
| Refusal on blur | `Date incomplète. Écrivez jj/mm/aaaa.` · `Cette date n'existe pas.` |
| Future date, `date_prescription` | Refused: `Une ordonnance ne peut pas être datée dans le futur.` |
| Future date, `date_naissance` | Refused: `Cette date de naissance est dans le futur.` |
| Transport | ISO `AAAA-MM-JJ` to the API. The screen never shows ISO |

## 16. The design problem of this phase, and this document's opinion about it

`04-CONTEXT.md` states it and asks for a position: **the failure mode is not the out-of-range value,
it is the plausible typo.** An axe of `90` typed for `9` passes every bound and produces wrong lenses.

### 16.1 The position

> Validation catches the impossible. **Only the screen catches the implausible**, and it catches it
> in exactly three ways: by making the value *re-readable in the notation the paper uses*, by
> *showing it next to the last one*, and by *saying out loud, without refusing, that something looks
> odd*. Everything in §20 is one of those three.

Four layers, in increasing order of what they actually catch:

| Layer | Catches | Blocks? | Where |
|---|---|---|---|
| 1 · **Bornes** | The impossible: −40,00 sphère, axe 400, a step of 0,17 | **Yes**, on blur | §16.2 |
| 2 · **Relecture** | The plausible typo, by forcing a re-read in prescription notation | No — it is a display | §20.6 |
| 3 · **Comparaison** | The plausible typo, by putting the previous version beside the new one | No — it is a display | §20.7 |
| 4 · **Avertissements** | The implausible: additions that differ, an axe that moved 80°, a sphère past ±10 | **No, never** | §16.3, §16.4 |

Layer 5 is not on the screen at all: **CLIENT-06 versioning is the net under the whole thing.** A
mistake that gets through is correctable by a new version, and the wrong one stays readable. That is
why §21.2 refuses to let a stored version be re-validated on display.

### 16.2 Layer 1 — the bounds are served, never hardcoded in TypeScript

D-4b: *"Les bornes vivent à UN endroit nommé… le prochain changement doit coûter une ligne."*

**A TypeScript constant is a second named place.** So the bounds travel like the permission catalogue
labels already do (`03` §7.4): **the server sends them, the SPA renders them.**

```
GET /api/ordonnances/bornes/     (or the same object embedded in the ordonnance schema)
{
  "sphere":    {"min": "-20.00", "max": "20.00", "pas": "0.25", "signe_obligatoire": true},
  "cylindre":  {"min": "-10.00", "max": "0.00",  "pas": "0.25", "convention": "negatif"},
  "axe":       {"min": 1, "max": 180, "pas": 1},
  "addition":  {"min": "0.75",  "max": "4.00",  "pas": "0.25"},
  "ep_binoculaire": {"min": "45.0", "max": "85.0", "pas": "0.5"},
  "ep_monoculaire": {"min": "18.0", "max": "44.5", "pas": "0.5"}
}
```

- The SPA holds **no clinical number**. A CI grep for `20.00|-10.00|180|0.75` under
  `web/src/pages/clients/` is the cheap enforcement, exactly like the `audit:format` line.
- Client-side bound checking is a **convenience that keeps the counter out of a round trip**. The
  server refuses independently. No plan task may read "valider X dans l'interface" and be done.
- The two EP ranges are **this document's judgement, with no normative source** — see §28-Q4. The
  *mechanism* is not a judgement: they live in the same served object as the rest.

### 16.4 What a warning that is not a refusal looks like, and how it is announced

This is the design question `04-CONTEXT.md` asks, and it has a precise answer.

**Visually.** A warning is **quieter than an error, deliberately.**

| | Refusal (bound) | Warning |
|---|---|---|
| Colour | Destructive `#DC2626` text, destructive field border | **No colour at all.** Text `#18181B` on `#F4F4F5`, border `#E4E4E7`, icon `TriangleAlert` 16px in `#52525B` |
| Carrier of meaning | The word + the red | **The word `À vérifier —` and nothing else.** Phase 4 adds no colour (`03` §4: no green, no orange), and `03` §10 forbids colour as the sole carrier anyway |
| Placement | Immediately under the field, 4px gap | Under the **field group** (the eye's row, or the EP block), 8px gap, `max-w-prose` |
| Type | Label 12px/400 | Label 12px/400 |
| Persistence | Until the value is valid | Until the value stops being odd, or the version is saved |

**A warning that looks like an error trains the optician to dismiss both.** That is the whole reason
for the quieter treatment, and it is why introducing an orange would be worse than useless here.

**To a screen reader.** Three rules, and the second is the one that matters:

1. The note is `role="status"` (`aria-live="polite"`). **Never `role="alert"`** — warnings appear
   while typing and an assertive interruption per keystroke is hostile.
2. **`aria-invalid` is NOT set on a warned field.** `aria-invalid="true"` is a claim that the value
   is wrong; a warning claims only that it is unusual. Setting it would make a warning
   indistinguishable from a refusal to exactly the user who cannot see the colour difference above —
   which would undo the entire visual design in one attribute.
3. The note's `id` is in the field's `aria-describedby`, so returning focus to the field re-reads it.

**When.** Warnings are computed **on blur and on submit-attempt, never on change.** Typing `9` on the
way to `90` must not announce anything. Refusals follow the same timing.

**Announcement.** On blur, a newly-appeared warning is announced once, politely, in its own text. The
count also lives at the head of the relecture panel (§20.6): `2 points à vérifier.`

### 16.5 The one place a warning costs a click — and why that is not confirm fatigue

Submitting **while warnings are outstanding** opens one confirmation. Submitting with none opens
nothing.

shadcn `alert-dialog`, **non-destructive** (no `bg-destructive`, no typed confirmation), secondary
`Retour` per `03` §7.10 and the amended rule of `03` §7.9:

> ### Enregistrer malgré 2 points à vérifier ?
> • L'addition est normalement identique aux deux yeux. OD +2,25, OG +2,00.
> • L'axe OD passe de 90° à 9° depuis le 14/03/2025.
>
> Vous pourrez corriger par une nouvelle version : celle-ci restera lisible telle qu'elle a été saisie.
>
> `[ Retour ]`   `[ Enregistrer l'ordonnance ]`

- The second sentence states **what survives**, which is the rule `03` §7.9 sets for every
  confirmation in this product. Here what survives is the whole point of CLIENT-06.
- A warning you can walk past with zero friction is not a control. A confirmation that appears only
  when something is genuinely odd is rare by construction — which is the difference between this and
  the 21-switch confirm fatigue that `03` §7.8 refuses.
- **No "j'ai vérifié" checkbox, and no column recording that the optician was warned.** That is
  consent theatre and a field nobody reads. The version history is the record.

Inherited unchanged. **No new size, no new weight.** Two assignments worth pinning because they are

- A relecture line (`OD +2,00 (−1,00 à 90°) Add. +2,25`) is **Heading 18/600 with `.chiffres`**

- Every clinical value, everywhere — form, fiche, history, print — is `tabular-nums`. A column of
  corrections in proportional digits is unscannable for the same reason a column of amounts is
  (`03` §3).

### 17.3 Colour

**Phase 4 introduces no colour.** This is the checkable claim of the whole warning design (§16.4):

- Accent `#2563EB` keeps exactly the five uses of `03` §4. On these screens that means: the one
  primary button per screen (`Créer un client`, `Saisir une ordonnance`, `Enregistrer l'ordonnance`),

- Destructive `#DC2626` keeps its three uses. On these screens: bound-refusal text and field border,
  and the `Quitter sans enregistrer` confirm button. **Nothing about an ordonnance is red** — not a
  superseded version, not a warning, not a strong correction.
- Badges (`Correction`, `Renouvellement`, `Ordonnance médicale`, `Réfraction opticien`,
  `Version en cours`, `Remplacée`) are **neutral badges carrying the word**, per `03` §4.

## 20. Surface E — Saisie d'une ordonnance (`/clients/:id/ordonnances/nouvelle`)

**The densest screen in the product after `Comptes et droits`.** It is filled by someone reading off a
paper prescription, so tab order and numeric entry matter more than every mouse affordance on it.

### 20.1 A route, not a dialog

Deliberate. A dialog would trap focus, cap the width, and make the relecture panel (§20.6)
impossible to place. Title Display 24/600 `Nouvelle ordonnance`, subtitle the client's name in
`<bdi>`. Gate: `ordonnance.saisir` (which `03` §7.6 makes depend on `ordonnance.voir`).

Its escape hatch is labelled **`Fermer`**, per `03` §7.10 — not `Annuler`, which in this product
means undo and only ever appears on an undo toast.

**No predicted version number is shown before saving.** The version is server-issued. Printing
`Ce sera la version 3.` on the form is the same habit that produces a client-issued facture number,
which CLAUDE.md #3 forbids for a reason that transfers exactly.

### 20.2 Field order — the paper's order, not the model's

A Moroccan/French ordonnance is written as a table: rows OD/OG, columns Sphère · Cylindre · Axe ·
Addition. **The form is that table, and the tab order is row-major across it.**

```

            Sphère      Cylindre    Axe      Addition        (dernière ordonnance, 14/03/2025)

  OG      [ +1,75  ]  [ −0,75  ]  [175 ]°  [ +2,25  ]         +1,75 (−0,75 à 175°) Add. +2,25

  OD      [ 31,5 ] mm        OG  [ 30,5 ] mm            somme : 62,0 mm

  Prescripteur          [ Dr. Bennani                    ]

  Motif                 [                                 ]

```

**Tab order, exactly:** notation → OD sphère → OD cylindre → OD axe → OD addition → OG sphère → OG
cylindre → OG axe → OG addition → EP form → EP fields in the order shown → source → prescripteur →
date → magasin → type de saisie → motif → photo → `Enregistrer l'ordonnance` → `Fermer`.

That is also the DOM order and the visual order. **No positive `tabindex` anywhere** (`03` §5.7).

**The reference column on the right is not in the tab order** — it is `aria-hidden` static text
duplicated into the relecture panel's accessible summary. It is a comparison aid for the eye.

### 20.3 The notation toggle — does the screen ever show the transposed form?

**Yes, in two places, and it is never what is stored.** The question was raised by
`04-CONTEXT.md` D-4 point 4 and by `04-RESEARCH.md` §6.1, and both halves of the answer matter.

*Why show it at all.* Ophthalmologists prescribe in minus-cyl; **opticians and labs work in plus-cyl
and transpose daily**, and CLIENT-08 sends these values to a fournisseur. A screen that only refuses
a positive cylinder makes the optician do the transposition in their head — and a mental
transposition error passes every bound in §16.2. That is the plausible-typo failure mode with an
extra step bolted on.

*Why it is never stored.* One convention, one column, one place (D-4b). A second stored
representation is a second source of truth, and the two will disagree.

**The two places:**

1. **Entry.** A radio group at the head of the grid: `Notation : (•) Cylindre négatif ( ) Cylindre
   positif`. Default `négatif`, always.
   - While `positif` is selected, the cylindre fields accept `0,00 … +10,00` and the relecture panel
     shows **both** lines, labelled (§20.6).
   - Switching the toggle **transposes the values already typed, in place, visibly**, and announces
     it politely: `Transposé en cylindre négatif : OD +2,00 (−1,00 à 90°).`
   - The transposition is the pure function of `04-RESEARCH.md` §6.1 —
     `sphère' = sphère + cylindre`, `cylindre' = −cylindre`, `axe' = (axe + 90) mod 180`, `0 → 180` —
     living next to the model with its own test, and called by the client through the same served
     contract, never reimplemented in TypeScript.
   - On save, what leaves the browser is **minus-cyl**, whatever the toggle said.
2. **Output to the fournisseur.** The commande spéciale block renders plus-cyl with the convention
   printed on the page. That is Phase 8's verification (`04-RESEARCH.md` §3.4); Phase 4 owns the
   function and the read-only rendering.

The convention is stated **on the screen**, not just in the code: a muted Label line under the grid,
`Les valeurs sont enregistrées en cylindre négatif.` `04-CONTEXT.md` asks for exactly this — so that
a convention error shows up on the first entry rather than on the first wrong pair of lenses.

### 20.4 Numeric entry — what a fast typist needs

| Rule | Contract | Why |
|---|---|---|
| Input type | `type="text" inputmode="decimal"`, **never `type="number"`** | Spinners, wheel-scroll value changes, and a `,` that yields `valueAsNumber = NaN` in a French interface |
| Decimal separator | Both `,` and `.` accepted while typing; normalised to `,` on blur | The counter's numeric keypad emits `.` |
| Normalisation on blur | `2` → `+2,00` · `-1` → `−1,00` · `,75` → `+0,75` · `31.5` → `31,5` | Two decimals for sphère/cylindre/addition, one for EP, integer for axe |
| Minus sign | Typed `-` (hyphen) is accepted; **displayed as U+2212 `−`** | A hyphen at 14px next to a `+` is ambiguous on a dense grid |
| Sphère sign | **Required.** A sphère with no sign is refused on blur: `Indiquez le signe : +2,00 ou −2,00.` | `+2,00` and `−2,00` are opposite lenses. This is the one field where the sign must be typed |
| Cylindre sign | **Supplied.** In `négatif` mode `1,00` → `−1,00`; `+1,00` → refused with `En cylindre négatif, le cylindre ne peut pas être positif. Basculez la notation ci-dessus si l'ordonnance est en cylindre positif.` | Convention, stated where it is broken |
| Addition sign | **Supplied**, always `+` | |
| Step | A value off the 0,25 grid is **refused**: `Les valeurs vont par pas de 0,25.` | **Never silently rounded** — a rounded value is a wrong number with no error, which the ORM layer already refuses server-side |
| Axe | Integer, `°` rendered as a suffix outside the input. `0` is accepted and canonicalised in place to `180`, announced: `Un axe de 0° et de 180° est le même axe. Enregistré comme 180°.` | Reconciles CLIENT-07's literal `0–180` with D-4b's stored `1..180` (`04-RESEARCH.md` §6.2) |
| Empty | An empty field is empty, never `0`. Server stores `null` | `0,00` and "not measured" are different facts |
| Cylindre of exactly `0` | Stored `null`, and the axe clears with it | `04-RESEARCH.md` §6.2 |
| Axe ↔ cylindre | Cylindre without axe: `Le cylindre de l'œil droit demande un axe.` Axe without cylindre: `Un axe sans cylindre n'a pas de sens. Saisissez le cylindre, ou effacez l'axe.` Both are **refusals**, checked on submit | The cross-field class that no range check catches |
| `Enter` | Submits the form, per `03` §5.7 — the form has exactly one primary action | And that is why §16.5's confirmation exists |

### 20.5 Écart pupillaire

Radio group `Écart pupillaire : ( ) binoculaire ( ) monoculaire ( ) les deux` writes `ep_saisi`. The
value is **stored, never inferred from which columns are null** (`04-RESEARCH.md` §3.2).

- Fields render per the choice; switching keeps any value that still applies.
- **The one sentence `04-RESEARCH.md` §6.5 asks the plan to commit to:**
  > **On enregistre ce qui a été saisi ; la somme binoculaire s'affiche comme contrôle quand les deux
  > monoculaires existent ; on ne calcule jamais un monoculaire.**
  Splitting a binocular value in two assumes the symmetry that progressives are exactly sensitive to.
- The displayed `somme : 62,0 mm` is a **display**, never a stored field and never submitted.
- **[AMENDÉ 2026-09-18 — 04-CONTEXT.md Q4]** Roadmap criterion 3 — "a monocular value entered where
  a binocular is expected" — **est un AVERTISSEMENT, plus un refus.** Le discriminant reste 45 mm et
  les deux messages restent les mêmes, préfixés `À vérifier — ` :
  - binoculaire < 45,0 → `Un écart binoculaire de 31,5 mm est un écart monoculaire. Choisissez « monoculaire » ci-dessus.`
  - monoculaire > 44,5 → `Un écart monoculaire de 62,0 mm est un écart binoculaire. Choisissez « binoculaire » ci-dessus.`
  Each message names the fix, not the rule. The two thresholds are `[JUGEMENT]` (§28-Q4); the
  mechanism is not — et c'est précisément pourquoi la sévérité a changé et pas le mécanisme.
  **La clause « refused at entry » du critère 3 de la feuille de route n'est donc plus
  littéralement satisfaite.** Elle est servie en substance : la valeur est détectée et nommée, avec
  la correction à faire. Réversion : rendre `severite: "refus"` aux lignes A8/A9 de
  `verifier.ts` — une ligne — le jour où un opticien confirme le seuil.
  Le champ de saisie, lui, accepte désormais l'**union** des deux plages servies ; au-delà, c'est
  un refus de borne ordinaire. Conséquence à connaître : le serveur, lui, refuse toujours un
  binoculaire sous 45,0 par sa `CheckConstraint` — voir `deferred-items.md`.

**Why a panel and not a confirmation dialog.** A dialog that restates the same numbers in the same

- Heading 18/600, `tabular-nums`, `LigneDeCorrection` (§19.3).

- `2 points à vérifier.` is the `role="status"` count of §16.4. Zero warnings renders no line at all,

- Empty form: the panel renders its headings with no values rather than disappearing. A panel that

### 20.7 Layer 3 — the previous version, beside the new one

When the client already has an ordonnance, its values render as a static reference column to the

This is what powers warnings A4, A5 and A6, and it is free — the previous version is already fetched
for §19.3.

**No automatic prefill.** A prescription that appears in the fields without being typed is a
prescription nobody read. When `Type de saisie = Renouvellement` is chosen, a ghost button
`Reprendre la précédente` appears; pressing it fills the fields visibly and announces
`Valeurs du 14/03/2025 reprises. Vérifiez-les sur l'ordonnance.` The reference column stays visible
either way.

**No retrospective diff view between two versions in Phase 4.** The moment where a comparison prevents
an error is *during entry*, and that is covered. A diff is a nice-to-have; deferred with reason.

### 20.8 Source, prescripteur, date (CLIENT-04, CLIENT-05)

- `Source` is a radio group: `( ) Ordonnance médicale ( ) Réfraction opticien`. No default —
  a pre-selected source is a clinical claim nobody made. Refused on submit if unset:
  `Indiquez la source : ordonnance médicale ou réfraction opticien.`
- `Prescripteur` is required **iff** source is `Ordonnance médicale`; refused otherwise with
  `Qui a prescrit ? Indiquez le médecin.` With `Réfraction opticien` the field is **not rendered**
  (there is no prescripteur to name), and the helper reads
  `La réfraction a été faite au magasin. Aucun prescripteur à indiquer.`
- `Date de prescription` uses `ChampDate` (§15.4). Required. Not in the future.

### 20.9 The magasin field — an extension of `03` §5.4, and why it is a field and not a page prompt

D-4a: an ordonnance is **client-wide**; it **carries the magasin that recorded it, for provenance
only**. So this screen needs a magasin even though its data is not magasin-scoped.

`03` §5.4 says a route that requires a magasin, reached under `Tous les magasins`, renders the
`InviteChoixMagasin` prompt instead of guessing. **That rule is not applied here, deliberately:**

> §5.4 exists because the *content* of a magasin-scoped screen would otherwise be silently wrong — a
> caisse balance for a magasin nobody chose. Here the content is client-wide and correct; exactly one
> **recorded value** is unknown. A full-page prompt would claim the screen is unusable when it is
> not, and would cost a click on every single entry. A field is the proportionate control, and
> guessing is still refused.

| Situation | Control |
|---|---|
| The user holds one magasin | Static line `Magasin : Anfa`, no control — the `03` §7.3B precedent: no decision, no control |
| Active scope is a named magasin | Radio group (≤4 magasins) or a **named** combobox, pre-selected to the active scope |
| Active scope is `Tous les magasins` | Same control, **nothing pre-selected**, refused on submit: `Indiquez le magasin qui enregistre cette ordonnance.` |

Label, visible: `Magasin qui enregistre`. Helper: `Sert à la traçabilité. L'ordonnance reste visible
depuis tous les magasins.` — one line that pre-empts the misreading of D-4a, in the `03` §7.2 style.

**The combobox variant carries `aria-labelledby` pointing at that visible label** (§15.2, D-1).

### 20.10 Saving — online only, and there is nothing to undo

| | |


- Badges are neutral and carry the word (`03` §4): `Version en cours`, `Remplacée`, `Correction`,
  `Renouvellement`, `Ordonnance médicale`, `Réfraction opticien`. **Nothing here is red.** A
  superseded version is not an error.
- `Remplace la version 2` is a link that scrolls to and focuses that card.
- The provenance line names the magasin — provenance, never a filter (D-4a).
- Empty state:
  > ### Aucune ordonnance
  > Saisissez l'ordonnance du client pour commander ses verres et déclencher ses rappels.
  > `[ Saisir une ordonnance ]`

### 21.2 CLIENT-06, rendered literally: **a stored version is never re-validated on display**

The bounds and the convention live in one served place (§16.2) and the owner has already changed them
once. So:

> **Une version enregistrée se rend telle qu'elle a été saisie. L'affichage ne la revalide jamais.**

A version holding a value that today's bounds would refuse still renders, with **no warning, no error
badge, no annotation**. Anything else would make old records look wrong because the rules moved, which
is precisely the "readable exactly as entered" guarantee CLIENT-06 buys.

`À vérifier` notes are a property of the **entry form**, not of a stored ordonnance. They are never
rendered here.

### 21.3 Correcting a mistake

There is **no edit control and no delete control on an ordonnance, anywhere.** The word `Supprimer`
does not appear on these screens, exactly as it does not appear in the account UI (`03` §7.8).

Correcting means `Saisir une ordonnance` → `Type de saisie : Correction d'une saisie précédente` →
a `Motif` (free text, required for a correction: `Dites ce qui était faux. Cela restera lisible.`).
The new version carries `supersede`; the old one is untouched.

### 21.4 Reading a single version

`/clients/:id/ordonnances/:version` renders one card full width, for linking and for printing. Same
component, same rules.

### 21.5 Printing

`Imprimer` calls `window.print()` against `web/src/print.css` (`03` §8.4) — **no page geometry is
added here**, which was the point of shipping that file in Phase 3. Phase 4 adds one document block:

- Header: the client's name, the `raison_sociale`, the magasin, the version and its date.
- The `LigneDeCorrection` lines of §19.3 — the same component as the screen.
- The footer line **`Cylindre négatif.`** A printed correction with no stated convention is the wrong
  pair of lenses waiting to be ordered.
- Black on white. No photo on the printed sheet (a grey-smeared phone photo costs toner and proves
  nothing; the photo is evidence held in the record, not on the counter's printout).

## 22. Surface G — La photo de l'ordonnance (CLIENT-09)

### 22.1 Attaching

Inside the entry form, last block before the buttons.

- A real `<input type="file">` with a **visible** `<label>` `Photo de l'ordonnance` and a styled
  button `Ajouter une photo`. Drag-and-drop onto the zone is an enhancement; the file picker is the
  contract, and it is keyboard-reachable because it is a real input.
- `accept="image/jpeg,image/png,image/webp,image/heic"`. **No PDF in Phase 4** — a PDF needs a
  viewer, and the document path is Phase 9's. Recorded as deferred, not forgotten.
- No `capture` attribute. Photographing at the counter is the Phase 11 Expo app's job.
- Helper: `Conservez la photo du papier : elle sert de justificatif pour un remboursement AMO.`
- Size check before upload, 10 Mo: `Cette image fait 14 Mo. La limite est de 10 Mo.` — mégaoctets,
  never bytes, never a MIME type on screen.
- Wrong type: `Ce fichier n'est pas une image. Formats acceptés : JPG, PNG, WEBP, HEIC.`
- **The upload error copy never echoes the filename.** An uploaded filename routinely carries the
  patient's name (`ordonnance_benali_ahmed.jpg`), and an error string is the one string in the
  product that reliably reaches Sentry. `04-RESEARCH.md` §4.6 has the matching server-side one-liner
  (`SENSITIVE_KEY` covers neither `photo` nor `fichier`).

### 22.2 Viewing

- Thumbnail 96px next to the version. `Voir la photo` opens a shadcn `dialog`, image at `max-height:
  90vh`, `alt=""` with the dialog titled `Photo de l'ordonnance — version 2` (the image carries no
  information a screen reader can use; the title does).
- The bytes come from an **authenticated DRF route** that has already resolved `ordonnance.voir` —
  never a `MEDIA_URL`, never a pre-signed URL (`04-RESEARCH.md` §4.4). So `<img src>` is an API path
  and a failure renders `messageChargementImpossible("la photo")` from `web/src/etats/messages.ts`,
  not a broken-image glyph.
- ~~The filename is displayed beside the thumbnail, truncated to 40 characters, in `<bdi>`~~
  **[AMENDÉ 2026-09-19 — plan 04-09, D-4-4]** **Le nom du fichier n'est affiché nulle part, parce
  qu'il n'est conservé nulle part.** Le plan 04-06 a délibérément refusé de le stocker : le nom
  sur disque est un identifiant aléatoire, aucune colonne ne le porte, et les six clés sous
  lesquelles il voyage sont caviardées avant la télémétrie — précisément parce qu'un nom de
  fichier d'ordonnance porte couramment le nom du patient (`ordonnance_benali_ahmed.jpg`).
  L'afficher supposerait de le ré-introduire en base pour un confort, contre une donnée de santé.
  **Ce qui le remplace comme contrôle de mauvaise pièce jointe : la vignette** — qui montre le
  papier lui-même, donc dit strictement plus — **plus `Photo attachée le 12/02/2026 à 10:02`**,
  servi par `photo_attachee_le`. La règle qui survit de cette ligne est son dernier tiers, et elle
  est absolue : aucun nom de fichier n'apparaît dans un titre de page, un toast ou une erreur.

### 22.3 A photo is attached once and never replaced

The row is immutable (CLIENT-06). Consequences, stated so nobody quietly adds an `UPDATE` path:

- A version **saved without a photo may receive one later** — the paper often arrives the next day.
  That is a one-way `null → set` transition and the only mutation this phase permits on an ordonnance.
- A photo is **never replaced and never deleted.** The control says so:
  `Une photo ne se remplace pas. Pour corriger, enregistrez une nouvelle version.`
- Whether `null → set` is acceptable on an otherwise immutable row is a **model** question, not a
  rendering one: §28-Q5.

## 25. Accessibility — Phase 4 additions to `03` §10

`03` §10 applies in full. What follows is only what this phase adds.

### 25.1 The warning, and the attribute that is deliberately absent

§16.4 is the contract: `role="status"`, in `aria-describedby`, **no `aria-invalid`**, announced on
blur and never on change. Named test:
`un avertissement ne porte pas aria-invalid et n_est pas role=alert`.

### 25.2 Every new combobox has a name — the D-1 lesson

Phase 4 introduces exactly one potential `role="combobox"`: the magasin field of §20.9, and only when
the business has five or more magasins. It carries `aria-labelledby` pointing at the visible
`<label>` `Magasin qui enregistre`.

**Everything else that could have been a combobox is a `radiogroup` instead** — notation, EP form,
source, type de saisie. Three reasons, in order: the options are all visible, which a counter reads
faster; arrow-key navigation is native; and a radio group takes its name from a real `<legend>`, so
the name-from-author trap that produced D-1 cannot occur.

Named test, and it must enumerate rather than spot-check:
`tout combobox de la phase 4 a un nom accessible non vide` via `computeAccessibleName`.

### 25.3 The OD/OG grid

- CSS grid, not a `<table>` — it is a form, and a table of inputs makes a screen reader announce
  coordinates instead of meaning.
- Each input has a **real, visually hidden `<label>` carrying the whole meaning**: `Sphère de l'œil
  droit`, `Axe de l'œil gauche`. Not `aria-label` — a `<label>` also enlarges the click target.
- The visible column headers (`Sphère`, `Cylindre`, `Axe`, `Addition`) are `aria-hidden` so nothing
  is read twice.
- The visible row labels `OD` / `OG` are followed by a visually hidden `œil droit` / `œil gauche`.
  A screen reader that spells out `OD` tells the user nothing.
- The `°` suffix is outside the input and `aria-hidden`; the hidden label already says `Axe`.
- The reference column (§20.7) is `aria-hidden`; its content is in the relecture panel's text.

### 25.4 Focus

- Submit failure moves focus to the inline error above the button (`03` §5.7).
- The save-with-warnings dialog returns focus to `Enregistrer l'ordonnance` on `Retour`.
- Route change to the history moves focus to the `h1` and announces it (`03` §10).
- `Reprendre la précédente` returns focus to the first sphère field after filling.

### 25.5 What jsdom cannot verify, stated honestly

`04-CONTEXT.md` lists it among the four traps already paid for in Phase 3: **jsdom computes no CSS.**
So a vitest assertion can prove that the warning note exists, that it has `role="status"`, that it is
referenced by `aria-describedby` and that it does **not** set `aria-invalid` — and it can prove that
the element's class list does not contain a destructive token. It **cannot** prove that the warning
reads as quieter than an error, that the focus ring is visible, that the 416px grid does not wrap at
1280px, or that the relecture panel is legible beside the paper.

**Five manual checks, and only five.** The Phase 3 balance of 18 is still open, so this phase adds a
deliberately short list:

1. At 1280px, the grid, the reference column and the relecture panel coexist without wrapping.
2. A warning and a refusal, side by side on one screen, are distinguishable **in greyscale**.
3. The focus ring is visible on every field of the grid, including the axe input with its `°` suffix.
4. A printed ordonnance is legible and carries `Cylindre négatif.`
5. NVDA or VoiceOver on the entry form: a warning is announced politely once, and the field is not
   announced as invalid.
