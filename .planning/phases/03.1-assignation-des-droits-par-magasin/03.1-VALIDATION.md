# Validation de la phase 03.1 — Assignation des droits par magasin

Ce document est renseigné par le plan `03.1-04`. Il est écrit **avant** l'exécution pour
que les critères soient fixés d'avance plutôt que dérivés de ce qui a été livré.

Deux principes en gouvernent la forme :

1. **Les nombres se relèvent, ils ne se recopient pas.** Les colonnes « attendu » sont une
   prévision de planification ; seule la colonne « observé » fait foi.
2. **Aucun critère n'est le grep d'un mot nu.** Le piège s'est produit **sept fois en phase
   3** : un critère qui cherche un mot que la prose du dépôt contient aussi passe ou échoue
   pour la mauvaise raison. Chaque garde ci-dessous cherche une ligne d'`import`, une
   affectation, un symbole encadré de `\b`, ou l'absence de sortie d'une commande `git`.

## 3. La passe humaine — six étapes

Une personne, un navigateur. **Trois des cinq défauts de la phase 3 ont été trouvés ainsi
pendant que 303 tests étaient verts**, et deux d'entre eux relèvent d'un jugement qu'aucune
suite n'attrapera jamais. La découvrabilité d'un contrôle est de cette classe — c'est
exactement la plainte qui a créé cette phase.

Préparation : `docker compose up -d`, `uv run python manage.py runserver`,
`npm --prefix web run dev`. Deux affaires sont nécessaires : celle **à deux magasins**
(Anfa, Maârif) pour les étapes 1 à 5, celle **à un magasin** pour l'étape 6.

| # | Étape | Ce qui est jugé, et que la suite ne peut pas juger | VERDICT |
|---|---|---|---|
| 1 | Découvrabilité du sélecteur | Il se **voit** sans survol. jsdom ne calcule pas le CSS : la suite prouve l'absence de classe de révélation, jamais la visibilité. Et : a-t-il été confondu, ne serait-ce qu'une seconde, avec le sélecteur du shell ? | {à renseigner} |
| 2 | **L'ouverture : `Tous` ou un magasin nommé** | Le propriétaire a le dernier mot, l'écran sous les yeux. Voir §5 pour le coût chiffré du renversement. | {à renseigner} |
| 3 | Le mode « un magasin » | Phrase de portée juste, droits éteints là où ils ne sont pas détenus, badge `Personnalisé` conservé | {à renseigner} |
| 4 | Plus rien par ligne | Sur une fiche portant un droit personnalisé : aucun `Par magasin`, aucune sous-liste, aucun `Uniformiser` | {à renseigner} |
| 5 | Le dialogue d'ajout | Rien ne bouge derrière lui ; l'option par défaut est la bonne ; **les deux chiffres sont justes, comptés à la main** ; `Retour` laisse tout intact | {à renseigner} |
| 6 | Le mono-magasin | L'affaire à un magasin n'a **rien gagné** : ni sélecteur, ni dialogue. C'est le cas fréquent. | {à renseigner} |

Le verdict s'inscrit **mot pour mot** tel que le propriétaire l'a formulé. Un verdict lissé
à l'écrit est un défaut perdu.

## 5. Le renversement de D-1a, chiffré d'avance

Si l'étape 2 est rejetée — le propriétaire veut que le sélecteur ouvre sur un magasin
nommé — **ne pas l'implémenter dans le plan `03.1-04`.** L'inscrire ici comme travail
suivant. Le coût est déjà connu, et c'est pour cela qu'il est écrit avant d'avoir la
réponse :

1. la constante `MODE_PAR_DEFAUT` de `web/src/pages/comptes/SelecteurDeMagasinDesDroits.tsx`
   passe de `null` au premier magasin accordé ;
2. **un amendement à CLAUDE.md #13, daté et motivé, dans le même changement** — pas une
   conséquence silencieuse. C'est la condition que le CONTEXT pose, et elle ne se négocie
   pas ;
3. deux tests nommés réécrits : `rend le sélecteur … et ouvre sur « Tous les magasins de ce
   compte »` et `porte TOUS les magasins accordés sur le fil tant que le mode est « Tous »`,
   dont le second change de sens ;
4. et la conséquence à accepter par écrit dans l'amendement : **le premier clic sur un
   compte neuf devient une personnalisation**, donc le badge `Personnalisé par magasin` de
   7.2 se lève sur tout compte réglé au défaut et cesse d'être un signal.
