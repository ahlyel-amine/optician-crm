# Phase 3 — UI Design Contract

> Visual and interaction contract for **Comptes, Permissions & App Shell**.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is the first UI in the project.** The shell defined here is inherited by Phases 4-12 without
redesign. Three surfaces ship: **Connexion**, **the app shell**, and **the owner's permission screen**.
Everything else in this document exists to stop those three from being rebuilt later.

**Upstream read:** `CLAUDE.md` (15 non-negotiables), `03-RESEARCH.md`, `ROADMAP.md`, `REQUIREMENTS.md`,
`PROJECT.md`, `research/FEATURES.md`. There is no `03-CONTEXT.md` — this phase never went through
`/gsd-discuss-phase`, so CLAUDE.md and the research are the binding inputs and every judgement call
below is labelled as such.

## 0. Where upstream is naive about the UI

Six corrections. Read these before the tables; three of them change what gets built.

### 0.1 The research's `DroitAccorde` drops the magasin dimension that CLAUDE.md #13 forbids dropping

`03-RESEARCH.md` §4 defines:

```
DroitAccorde(utilisateur, code)   UniqueConstraint(utilisateur, code)
AccesMagasin(utilisateur, magasin_code)
```

That is **one permission set per gérant plus a magasin list** — precisely the shape CLAUDE.md #13 says
must not be built: *"Permission grants are stored per (gérant, magasin, permission) … Do not 'simplify'
this to one permission set per gérant; reversing it is a data migration."* The research's own Open
Question 5 reaches the same doubt and calls it "the one decision here that is genuinely expensive to
reverse", then designs against it anyway.

**This UI-SPEC is written against CLAUDE.md #13**, because the interface it implies is the only one
that can honour both halves of the directive:

- storage is `(utilisateur, magasin_code, code)`;
- the UI writes **one row per granted magasin** when a switch is turned on, so the default experience
  is a single uniform checklist and the magasin dimension is invisible;
- a per-row **« Par magasin »** affordance (§6.4) is the only place the dimension ever surfaces.

The planner must reconcile the model with this. The constraint becomes
`UniqueConstraint(utilisateur, magasin_code, code)` and `Acces.peut(code)` gains a magasin argument, or
`Acces` is resolved per active magasin scope. **Raise it; do not quietly pick the research's shape.**

### 0.2 The permission catalogue has no "voir" code for ventes, so the nav cannot be gated

The ~20-code catalogue in §4 of the research contains `vente.creer`, `vente.remise`, `vente.voir_marge`
and `facture.avoir` — but nothing that means *"may look at the sales and invoices list"*. A gérant who
may consult a past facture but not create a sale is unrepresentable, and the **Ventes** nav entry has
no code to hang off. Same hole on the achats side: `fournisseur.voir` covers the directory but not the
bons de commande.

**Recommendation:** add `vente.voir` ("Consulter les ventes et les factures") to the catalogue in
Phase 3 and make `vente.creer` a prerequisite-dependent of it (§6.5). Catalogue goes from 20 to 21
codes. Codes are cheap; a missing dimension is not.

### 0.3 The login screen cannot carry per-client branding, and BRAND-01 will collide with that

There is **one shared login address** (CLAUDE.md #11). Before authentication the server does not know
which optician is typing, so it cannot serve their logo, colours or shop name. Phase 9's BRAND-01
success criterion — *"the application UI for that client shows them"* — is satisfiable for every
authenticated route and **not** for `/connexion`.

**Contract set now:** `/connexion` carries platform identity only. Per-client branding applies from the
first authenticated paint (§5.2). Do not design an email-first "who are you?" step to get around it —
it doubles the login flow and enumerates accounts across tenants.

### 0.4 The identifier should be an e-mail, because uniqueness is fleet-wide

Login names are unique across the **whole control plane**, not per client. If the owner of Optique Anfa
creates the gérant `karim` and it is already taken by another optician's gérant, the error message
"ce nom est déjà pris" discloses the existence of another business's account, and the owner has no way
to resolve it. Using an e-mail address makes the uniqueness domain natural and the collision essentially
impossible.

**Contract:** the identifier field is `Adresse e-mail` (`type="email"`, `autocomplete="username"`).
If the planner keeps free-form login names, the creation form must handle collision with copy that does
not confirm another account exists — e.g. *« Cet identifiant n'est pas disponible. Essayez
prenom.nom@votredomaine.ma. »* **[JUDGEMENT — flag to the developer.]**

### 0.5 Deferring the component library to Phase 4 (research §8) is wrong, and it costs Phase 9 too

The research defers picking a component library on the grounds that Phase 3 has "one form (login)".
It does not. Phase 3 needs a **modal dialog with a focus trap**, a **combobox** (magasin selector), a
**command palette** (search), **switches**, a **collapsible row**, a **toast with an undo action**, a
**dropdown menu** and a **data table**. An accessible dialog and an accessible combobox are the two
things the research's own "Don't Hand-Roll" table would forbid hand-rolling if it had noticed them.

Second, and larger: shadcn's theming model **is** CSS custom properties. The research already asks for
"CSS custom properties for colours now, so Phase 9 sets variables instead of rewriting styles". Adopting
shadcn in Phase 3 delivers that for free; adopting it in Phase 4 means restyling the shell.

**Reversed here:** shadcn/ui is initialised in Phase 3, Wave 0. See §1.

### 0.6 "Absent, not greyed out" cannot be maintained by discipline — it needs a mechanism

Roadmap criterion 4 and the phase brief both require that a field a gérant may not see is *absent*.
On the server, `03-RESEARCH.md` §3 gives that a mechanism (the registry + conformance test). On the
client there is currently nothing, and a hardcoded column array in a React table will re-introduce the
leak in Phase 8 by simply rendering `prix_achat: undefined` as an empty column with a header.

**Contract (§8.3):** every table and detail view declares columns/fields in a registry keyed by the API
field name, and the renderer **filters to the fields actually present in the payload**. A field the
server omitted cannot produce a header, a placeholder, a tooltip or a total. This is the client-side
half of PERM-06 and it is testable.

### 0.7 Smaller notes

- Roadmap criterion 3 (`prix d'achat`, marge, CA global) is not verifiable in Phase 3 — those fields
  land in Phases 8 and 10. The research is right. What Phase 3 owes is the **mechanism** (§8.3) plus
  the catalogue codes, proven against a test-only fixture resource.
- `FEATURES.md`: the market is crowded (800-4 000 DH/an) and the incumbents are desktop-era. The UI
  differentiator is not more screens — it is that **a gérant's application is visibly smaller than the
  owner's**. Hidden nav entries are a feature, not a punishment. Design copy accordingly.
- Support time is the dominant per-client cost at 2 400-12 000 MAD/year with one developer. Every
  permission row carries a one-line plain-French explanation (§6.3) and every destructive dialog states
  what survives the action. That is a cost decision, not decoration.

## 2. Spacing Scale

Declared values, all multiples of 4. This is a dense counter-and-back-office tool: the default step is
16, not 24.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap, badge inset, gap between a switch and its helper line |
| sm | 8px | Table cell vertical padding, gap inside a button, stacked form-field internals |
| sm+ | 12px | Table cell horizontal padding, gap between switch rows, nav item inset |
| md | 16px | Default gap between form fields, card inner padding, gap between toolbar groups |
| lg | 24px | Page padding, gap between cards, section padding inside a card |
| xl | 32px | Gap between the three regions of the account detail page |
| 2xl | 48px | Empty-state vertical breathing room |
| 3xl | 64px | Vertical centring offset on `/connexion` |

**Fixed dimensions** (all multiples of 4, all derived from the scale):

| Element | Value |
|---|---|
| Top bar height | 56px |
| Sidebar width, expanded | 240px |
| Sidebar width, icon rail | 56px |
| Default control height (button, input, select) | 36px |
| Compact control height (inline in a table row) | 32px |
| Table row height | 40px |
| Table header row height | 36px |
| Form column max width | 640px |
| Account detail content max width | 880px |
| Login card max width | 400px |

**Exceptions:**

1. **44px minimum hit target** for every icon-only control (WCAG 2.2 AA, 2.5.8). The *visual* box stays
   36px — a 44px visual icon button wrecks a dense toolbar — and the target is expanded with a
   pseudo-element. Specify it once in a `.cible-44` utility; never by inflating padding.
2. **2px focus ring with a 2px offset** sits outside the box model and is exempt from the scale.
3. No other exception. A value not in this table is a review failure.

## 3. Typography

Four sizes, two weights. Nothing else ships.

| Role | Size | Weight | Line Height | Used for |
|------|------|--------|-------------|----------|
| Display | 24px | 600 | 1.25 | Page title, one per route (`Comptes et droits`) |
| Heading | 18px | 600 | 1.30 | Card and section titles (`Magasins`, `Droits`) |
| Body | 14px | 400 | 1.50 | Everything: table cells, inputs, paragraphs, nav items, buttons (buttons use 600) |
| Label | 12px | 600 | 1.40 | Table column headers, form field labels above compact inputs, metadata, the helper line under a permission row (weight 400 at this size) |

- **Two weights only: 400 (regular) and 600 (semibold).** No 500, no 700. Buttons, active nav items and
  column headers get 600; everything else 400.
- **Minimum rendered text size is 12px.** Nothing smaller, including badges and timestamps.
- **No `text-transform: uppercase`, anywhere.** French uppercase loses or mangles accents in several
  system faces (`É`, `À`), and «  COMPTES DÉSACTIVÉS » is both harder to read and a support risk.
  Column headers are sentence case: `Dernière connexion`, not `DERNIÈRE CONNEXION`.
- **`font-variant-numeric: tabular-nums`** is mandatory on every money value, every date, every
  quantity and every reference. Applied through the `.chiffres` utility and baked into the money and
  date formatters' output wrapper. Proportional digits in a column of amounts is the single most
  common way a dense financial table stops being scannable.
- Body copy max line length 80 characters (`max-w-prose` on explanatory paragraphs only).

**Font stack** — no webfont is downloaded in v1 (a shop on a weak connection pays for it every load,
and the product is online-only so there is no cache guarantee):

```css
--police-ui:
  system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial,
  "Noto Sans Arabic", "Geeza Pro", "Segoe UI Historic", sans-serif;
```

The Arabic faces are **not optional**. Arabic client names must render correctly inside a French
interface (BRAND-04 upstream, CLIENT-01 downstream); a stack without an Arabic fallback produces
tofu boxes on Linux and on older Windows.

## 4. Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FAFAFA` canvas · `#FFFFFF` surface | Page background and every card, table and panel surface |
| Secondary (30%) | `#F4F4F5` sidebar & table header · `#E4E4E7` borders & separators · `#52525B` muted text | Chrome, structure, secondary text |
| Accent (10%) | `#2563EB` | See the reserved-for list below |
| Destructive | `#DC2626` | See below |
| Foreground | `#18181B` | Primary text |

**Accent `#2563EB` is reserved for, and appears nowhere else:**

1. The **one** primary button on a screen (`Se connecter`, `Créer un compte gérant`, the confirm button
   of a non-destructive dialog).
2. The **focus ring** — 2px, 2px offset, on every focusable element.
3. The **active nav item**: a 2px left indicator bar plus 600-weight label. The row background stays
   `#F4F4F5`; the accent is the bar, not a fill.
4. The **checked state** of a switch or checkbox.
5. The **selected row** of the command palette and of the magasin combobox.

It is **not** used for: links inside tables (those are `#18181B`, underlined on hover), icons in
general, informational badges, section headings, the sidebar background, chart series (Phase 10 gets
its own amendment), or "interactive elements" as a class.

**Destructive `#DC2626` is reserved for:**

1. The confirm button of a destructive dialog (`Désactiver le compte`, `Retirer l'accès au magasin`).
2. Form field error text, the field border in error, and the error summary.
3. The `Désactivé` account badge and — from Phase 7 — a negative amount or an overdue échéance.

**No third semantic colour.** There is no green and no orange in this product. `Actif` is a neutral
badge carrying the word `Actif`; `encaissé` (Phase 7) will be a neutral badge carrying the word. A
later phase that wants a success or warning hue must amend this document first. Rationale: with
per-client branding arriving in Phase 9, a client whose brand colour is green or red makes a semantic
palette ambiguous — and status colour unpaired with a word fails WCAG 1.4.1 regardless.

### Contrast floor

| Pair | Ratio | Verdict |
|---|---|---|
| `#18181B` on `#FFFFFF` | 16.9:1 | AA ✔ |
| `#52525B` on `#FFFFFF` | 7.6:1 | AA ✔ — muted text is zinc-600, never zinc-400 |
| `#FFFFFF` on `#2563EB` | 4.5:1 | AA ✔ at weight 600. Buttons are 600; do not drop to 400 |
| `#2563EB` ring on `#FFFFFF` / `#FAFAFA` | 4.5:1 / 4.3:1 | AA non-text (3:1) ✔ |
| `#DC2626` on `#FFFFFF` | 4.8:1 | AA ✔ |
| `#E4E4E7` border on `#FFFFFF` | 1.3:1 | Decorative only — a border is never the sole indicator of a control's bounds; inputs also carry a fill difference |

### Branding hook (Phase 9, BRAND-01) — built in now, costs one line

Every colour above is a CSS custom property on `:root`, emitted by shadcn's `cssVariables: true`.
Phase 9 sets **exactly two** of them per client, from the control plane, on an authenticated boot:

```css
--primary            /* the client's brand colour — replaces #2563EB */
--primary-foreground /* computed for AA contrast server-side, never guessed in CSS */
```

Hard rules, stated now so Phase 9 does not renegotiate them:

- **`--destructive` is never brandable.** A shop whose logo is red does not get a red destructive
  button and a red brand button on the same screen.
- The neutrals (`--background`, `--card`, `--border`, `--muted-foreground`) are **never brandable**.
  A client-chosen background is how a dense data tool becomes unreadable.
- The server supplies `--primary-foreground` next to `--primary` after checking 4.5:1. A brand colour
  that fails contrast is refused at upload, with French copy, not silently rendered.
- Branding is applied by setting variables on `:root` after `/api/auth/moi/` resolves — never by a
  second stylesheet, never by a class on `<body>` that components must know about.

### Dark mode

**Not in v1.** shadcn emits the `.dark` variable block by default; leave it, do not wire a toggle, do
not claim support. A counter under shop lighting works in light mode, and a second palette doubles the
Phase 9 branding contrast problem for zero requirement.

## 5. The App Shell

The highest-leverage artefact in this phase: nine later phases hang off it. Everything here is a
contract, not a suggestion.

### 5.1 Layout

```
+------------+---------------------------------------------------------+
| [logo] Optique Anfa  [v Tous les magasins]  [ Recherche...  Ctrl+K ]  |  56px
+------------+---------------------------------------------------------+
| Tableau…   |                                                          |
| Clients    |   contenu de la route            padding 24px            |
| Stock      |                                                          |
| Ventes     |                                                          |
| Caisse     |                                                          |
| Achats     |                                                          |
| Rappels    |                                                          |
| Paramètres |                                                          |
|   240px    |                                                          |
+------------+----------------------------------------------------------+
```

- Top bar `56px`, fixed. Sidebar `240px`, collapsible to a `56px` icon rail (state persisted per user
  in `localStorage`). Content scrolls independently; the top bar and sidebar do not.
- Page padding `24px`. The content region has **no max width** — Phase 5's stock table and Phase 6's
  facture lines need the full viewport. Individual **forms** cap at `640px` and **reading columns** at
  80 characters; a 14px input stretched across 1600px is unusable.
- A **skip link** `Aller au contenu` is the first element in the tab order, visible on focus.

### 5.2 Branding slot

Top-left renders the client's `raison_sociale` in Body/600, with the logo at 24px height once Phase 9
supplies one. Phase 3 renders the shop name only, in the same slot, at the same dimensions — Phase 9
adds an image element and changes nothing else. **The slot reserves 24 by 24px from day one** so adding
the logo causes no reflow. `/connexion` carries platform identity only, see 0.3.

### 5.3 Navigation — the nine-phase contract

Eight top-level entries, one slot reserved, **hard cap at nine**. A tenth module goes inside an
existing section or replaces one; it does not get a tenth row. Second-level navigation renders as a
row of section links inside the content area, **not** as a sidebar accordion — an accordion at this
size becomes a tree the user re-navigates on every visit.

| # | Entry | Route | Permission code | Phase | Second level (later) |
|---|---|---|---|---|---|
| 1 | Tableau de bord | `/` | none — any authenticated user; the CA-global widget is gated by `dashboard.voir_ca_global` | 10 | — |
| 2 | Clients | `/clients` | `client.voir` | 4 | Fiche, Ordonnances, Historique |
| 3 | Stock | `/stock` | `stock.voir` | 5 | Articles, Mouvements, Inventaire, Suivi de commande |
| 4 | Ventes | `/ventes` | `vente.voir` **(new code, see 0.2)** | 6 | Devis, Factures, Avoirs |
| 5 | Caisse | `/caisse` | `caisse.voir` | 7 | Journal, Comptage, Échéances chèques |
| 6 | Achats | `/achats` | `fournisseur.voir` | 8 | Fournisseurs, Bons de commande, Réceptions, Soldes |
| 7 | Rappels | `/rappels` | `rappel.voir` | 10 | Réappro, Échéances, Relances AMO |
| 8 | Paramètres | `/parametres` | `compte.gerer`, owner always | 3 | **Comptes et droits (Phase 3)**, Magasins, Personnalisation (9), Abonnement (12) |
| 9 | *reserved* | — | — | — | — |

**Ordonnances get no top-level entry.** They live inside a client's fiche as a tab. Hoisting them would
be the desktop-era mistake the incumbents make — an ordonnance detached from its client is not
something an optician looks for.

**Rendering rules:**

- The nav is one declarative array `NAV: {code, libelle, route, icone, disponible}[]`. Nothing renders
  a nav item from outside that array.
- An item whose `code` is not in `acces.permissions` is **not rendered** — no disabled state, no
  tooltip, no lock icon. A gérant's application is genuinely smaller, see 0.7.
- An item with `disponible: false` (module not built yet) is absent from a production build and
  **present** in dev behind `VITE_NAV_COMPLET=1`, so the layout is exercised at full density from
  Phase 3 and nobody discovers at Phase 8 that eight entries overflow.
- Active item: 2px accent left bar, 600 weight, `#F4F4F5` background. Hover: `#F4F4F5` only.
- Icons: lucide, 16px, `#52525B`, inheriting the label colour when active, `aria-hidden`. In the
  collapsed rail the label becomes a tooltip **and** an `aria-label` — never a tooltip alone.

> **The UI permission filter is convenience, never enforcement.** The server queryset scope and the
> projection layer are the control. No plan task may be written as "hide X in the UI" and marked done.

### 5.4 The magasin selector

Top bar, immediately right of the shop name. Phases 5, 6, 7, 8 and 10 all depend on this piece.

- **It is a scope filter, not a login context.** It never re-authenticates and never navigates.
- Options: every magasin in `acces.magasins` (from `/api/auth/moi/`), plus **`Tous les magasins`** when
  the user holds more than one.
- **A user with exactly one magasin sees a static label, not a dropdown.** No disabled select, no
  single-option menu. There is no decision, so there is no control — which means every single-shop
  optician (the `Essentiel` tier) and most gérants never meet this control at all.
- Default on first sign-in: owner gets `Tous les magasins`; a gérant gets their first granted magasin.
- Persistence: last selection in `localStorage` keyed by user id, **re-validated against
  `acces.magasins` on every bootstrap**. A revoked or deactivated magasin falls back silently to the
  first granted one. `localStorage` is a display preference; the server filters regardless.
- Mirrored into the URL as `?magasin=CODE` on magasin-scoped routes, so a link is shareable and a
  reload is stable. The URL wins over `localStorage` on load.
- Changing scope invalidates every react-query key containing the magasin and announces
  `Magasin : Anfa` in a polite live region. It never changes route.
- Control: shadcn `popover` plus `command`, searchable once a business has 10 or more magasins
  (`Chaîne` tier). Trigger is 32px compact height with a `ChevronsUpDown` icon.

**Route scope declaration — set now, saves Phase 7.** Every route declares `scope: "magasin" | "multi"`.
Some screens are inherently single-magasin (caisse, inventaire, mouvements de stock). When the scope is
`Tous les magasins` and the route requires one, the content area renders a **choice prompt**, never a
silent guess:

> ### Choisissez un magasin
> La caisse est propre à chaque magasin. Sélectionnez-en un pour continuer.
> `[ Anfa ]`  `[ Maârif ]`  `[ Californie ]`

Silently picking the first magasin and showing its caisse balance is the "wrong number with no error"
failure that `domaine/magasins/models.py` already refuses at the ORM layer. The UI refuses it too.

### 5.5 Search — the primary interface

Barcode scanning was deliberately excluded, which makes search how the counter finds things.

- Top bar, centred, `480px`, always visible once at least one search provider is registered.
- Opens with `/` or `Ctrl+K` from anywhere except while typing in another field.
- Debounce 200ms. Results grouped by type (`Clients`, `Articles`, `Factures`), max 5 per group.
  Arrow keys move, `Enter` opens the highlighted result, `Esc` closes and **returns focus where it
  was**.
- **Normalisation is server-side. The SPA sends the raw query and never filters client-side.**
  Accent-insensitive (`Bénali` equals `Benali`), case-insensitive, tolerant of Arabic transliteration
  variants (`Mohamed`, `Mohammed`, `Mhamed`) — CLIENT-10. The client's only job is to stay out of the
  way: no client-side filtering, no minimum query length above 2, no character stripping.
- **Exact-reference shortcut, scanner-ready, STOCK-07:** when the server marks a result
  `correspondance_exacte`, `Enter` navigates straight to it and the list is never rendered. A
  keyboard-wedge scanner types a reference and sends `Enter`; that must land on the article. The
  contract is set in Phase 3 so Phase 5 changes no shell code.
- Matched substring highlighted with **weight 600, not colour**.
- No results: `Aucun résultat pour « mohamed b »` — query echoed verbatim — plus the active provider's
  create action (Phase 4: `Créer un client « mohamed b »`).
- **Phase 3 has nothing to search.** The slot, the shortcut registration and the component ship; the
  field renders only when a provider is registered, and the slot keeps its 480px so the top bar does
  not reflow when Phase 4 lands.

### 5.6 Responsive behaviour

Desktop-first, explicitly. Mobile is a separate Expo app in Phase 11 (STACK.md rejected React Native
Web precisely because it is weakest at dense tables and keyboard flows). The web layout must still not
be hostile:

| Width | Behaviour |
|---|---|
| 1280px and above | Target. Sidebar expanded, full table density. |
| 1024 to 1279px | Sidebar auto-collapses to the 56px icon rail. Nothing else changes. |
| 768 to 1023px | Sidebar becomes an off-canvas drawer (shadcn `sidebar` provides it). Search collapses to an icon opening the palette full-width. Tables scroll horizontally with the **first column sticky**. |
| below 768px | Functional, not optimised. No route unreachable, no control off-screen, no horizontal scroll on the page body — only inside table wrappers. |

No mobile-specific screens, no separate mobile components, no touch-first controls. **Do not spend
design effort below 1024px.**

### 5.7 Keyboard contract

This tool is used all day at a counter. Keyboard flow is specified, not assumed.

| Key | Action | Scope |
|---|---|---|
| `Tab` and `Shift+Tab` | Move focus in **visual order**. No positive `tabindex` anywhere in the codebase. | Global |
| `/` or `Ctrl+K` | Open search | Global, except inside a text field |
| `Esc` | Close the topmost overlay and **return focus to its trigger** | Global |
| `Enter` | Submit the focused form when it has exactly one primary action | Forms |
| Arrow keys plus `Enter` | Navigate and choose in the search palette, the magasin combobox, any menu | Overlays |
| `Space` | Toggle the focused switch or checkbox | Controls |

- **No chorded or mnemonic shortcuts in v1** (`g` then `c`, `Alt+1`, and so on). Support time is the
  dominant per-client cost; an undiscoverable shortcut scheme is a training cost with no offsetting
  saving. Revisit at Phase 6, when the sale flow exists and there is a measured repetition to optimise.
- **The focus ring is never removed.** `outline: none` without a replacement ring is a review failure.
  2px `#2563EB`, 2px offset, on every focusable element including table rows that behave as links.
- Focus is trapped **only** inside a modal dialog, and restored to the trigger on close.
- When a submission fails, focus moves to the error summary at the top of the form.
- Autofocus: the first field of `/connexion`; the search input when the palette opens; the first
  control of a dialog. Nowhere else — an autofocus that steals the caret mid-typing is worse than none.

| State | Behaviour and copy |
|---|---|
| Idle | Button enabled once both fields are non-empty. Never disabled on an empty form without explanation — an inert button with no reason is a support call. |

| Deactivated account | **Same message.** A deactivated gérant must not learn they were deactivated from the login screen; the owner tells them. |
| Rate limited (429) | `Trop de tentatives. Réessayez dans une minute.` Button disabled for the remaining window with a live countdown in the help line. |

| Success | Route to the attempted path if one was stored, else `/`. Branding variables applied before the first authenticated paint, so the shell never flashes default blue then the client's colour. |
| Forced password change | If `doit_changer_mot_de_passe`, land on `/mot-de-passe` — a full-page, non-dismissible route with no shell nav. network error state, not as a silent broken submit.

## 7. Surface B — Comptes et droits (`/parametres/comptes`)

The hard surface. Roughly 21 permissions, N magasins, and an optician who must not need training.

### 7.1 The design problem, stated

Naive designs and why they fail here:

| Design | Why it fails |
|---|---|
| RBAC matrix, permissions by magasin | 21 by N checkboxes. At 3 magasins that is 63 controls on one screen. Forbidden by the phase brief and useless to the user. |
| Role tiers (`Gérant standard`, `Caissier`) | Forbidden by CLAUDE.md #6. A preset is a tier with a friendly name. Also the only permission-model differentiator `FEATURES.md` found in this market. |
| Flat checklist, no magasin dimension | What `03-RESEARCH.md` §4 designed. Reverses CLAUDE.md #13 and is a data migration to undo (see 0.1). |
| Checklist plus per-magasin override on request | **Adopted.** The common case is one checklist; the grid exists only where the owner asked for it. |

### 7.2 Account list (`/parametres/comptes`) — PERM-02

Page title Display `Comptes et droits`. Primary CTA top-right: **`Créer un compte gérant`**.

Table, 40px rows, row click opens the detail:

| Column | Content |
|---|---|
| `Nom` | Body/400. Wrapped in `bdi` so an Arabic name cannot reorder the surrounding punctuation. |
| `Adresse e-mail` | `#52525B`, tabular numerals off, `bdi` not needed. |
| `Magasins` | `Tous` for the owner; otherwise the magasin names, or `3 magasins` above two. |
| `Droits` | Count: `12 droits`. `Personnalisé par magasin` badge when at least one grant is non-uniform. |
| `Statut` | Neutral badge `Actif`, destructive badge `Désactivé`. The word carries the meaning; the colour only reinforces it. |
| `Dernière connexion` | `14/09/2026 à 09:14`, tabular numerals, or `Jamais connecté`. |

The owner's own row is first, labelled `Propriétaire`, and is **not clickable into a droits editor**
(7.6).

**Empty state** (a business with no gérant yet — the common case at onboarding, and the first thing a
prospect sees inside the product):

> ### Aucun compte gérant
> Créez un compte pour chaque personne qui tient un magasin. Les vendeurs n'ont pas besoin de compte —
> ils sont enregistrés sur la vente.
> `[ Créer un compte gérant ]`

That second sentence is deliberate: it pre-empts the single most likely misunderstanding of
CLAUDE.md #6 and costs one line instead of a support call.

**Creation dialog** (shadcn `dialog`, 480px): `Nom complet`, `Adresse e-mail`, `Mot de passe provisoire`
with a `Générer` button, and a read-only note `Ce mot de passe devra être changé à la première
connexion.` Confirm label `Créer le compte`. On success the dialog closes, the new row is highlighted
for 2 seconds, and the route goes straight to the detail page — because a freshly created account has
no droits and no magasin, which is the next thing to do.

### 7.3 Account detail (`/parametres/comptes/:id`) — three regions, in this order

Content max width `880px`. Regions separated by `32px`. The order is load-bearing: magasins before
droits, because a droit with no magasin grants nothing.

```
Karim Benali                          [Actif v]  [Réinitialiser le mot de passe]
karim.benali@optiqueanfa.ma
--------------------------------------------------------------------------------
A.  Identité      nom, e-mail, statut, réinitialisation du mot de passe
B.  Magasins      quels magasins ce compte peut voir            (PERM-04)
C.  Droits        ce que ce compte peut y faire                 (PERM-03)
D.  Historique    journal replié, lecture seule                 (JournalDroit)
```

**A — Identité.** Name and e-mail editable inline. `Statut` is a dropdown, not a switch: a switch
implies an instant toggle, and deactivation deserves a confirmation (7.8). `Réinitialiser le mot de
passe` opens a dialog showing a generated password once, with a `Copier` button and the line
`Notez-le maintenant : il ne sera plus affiché.` — because there is no email path.

**B — Magasins (PERM-04).** A checkbox per magasin of the business, with the magasin code as muted
secondary text.

- **A business with exactly one magasin renders a static line, not a checkbox:**
  `Magasin : Anfa`, helper `Ce compte a accès au seul magasin de l'entreprise.` Zero decisions where
  only one answer is possible. This is the single biggest simplification available, and it covers the
  whole `Essentiel` tier.
- Unchecking the last magasin is refused inline: `Un compte doit avoir accès à au moins un magasin.
  Désactivez plutôt le compte.` — the last clause is a link that opens the deactivation dialog.
- Removing a magasin that carries per-magasin overrides warns first (7.8).
- Section helper, always present: `Ce compte ne verra que les données des magasins cochés — clients,
  stock, ventes et caisse compris.`

**C — Droits (PERM-03).** See 7.4 and 7.5. The section header carries the scope sentence:

- one magasin: `Ces droits s'appliquent au magasin Anfa.`
- several: `Ces droits s'appliquent à tous les magasins de ce compte (Anfa, Maârif).` — magasins named
  rather than counted, up to four; beyond that, `à ses 6 magasins`.

**D — Historique des droits.** A `collapsible`, closed by default, read-only, newest first:
`14/09/2026 à 09:14 — Amine El Fassi a accordé « Voir le prix d'achat »`. It answers the question the
owner eventually asks ("who gave Karim the margins?") and it is the only view of `JournalDroit`.

### 7.4 The checklist — the core of the screen

The 21 codes are grouped into seven sections that **match the navigation exactly** (5.3). Matching
matters: an owner who grants `Consulter la caisse` should be able to predict that a `Caisse` entry
appears in Karim's sidebar.

| Section | Codes |
|---|---|
| Clients et ordonnances | `client.voir`, `client.modifier`, `ordonnance.voir`, `ordonnance.saisir` |
| Stock | `stock.voir`, `stock.ajuster`, `article.voir_prix_achat` |
| Ventes et factures | `vente.voir` *(new)*, `vente.creer`, `vente.remise`, `vente.voir_marge`, `facture.avoir` |
| Caisse | `caisse.voir`, `caisse.saisir`, `caisse.comptage` |
| Fournisseurs et achats | `fournisseur.voir`, `achat.commander`, `achat.voir_soldes` |
| Rappels et tableau de bord | `rappel.voir`, `dashboard.voir_ca_global` |
| Comptes | `compte.gerer` |

**Row anatomy** — 56px tall, `12px` between rows, `1px #E4E4E7` separator:

```
[ switch ]  Voir le prix d'achat                        [ Par magasin ]
            Le prix payé au fournisseur. Sans ce droit,
            la marge est également masquée, partout.
```

- Switch on the **left**, at the start of the reading direction. Label Body 14px/400, clickable, and it
  is the accessible name of the switch.
- **Every row carries a one-line explanation** in Label 12px/400 `#52525B`. Not a tooltip — a tooltip is
  invisible to someone scanning the screen, and this line is the support-cost lever. Written in plain
  French, naming the consequence rather than the code.
- Labels come from the **server's permission catalogue** (`/api/auth/moi/` or
  `/api/comptes/catalogue/`). The SPA never hardcodes a permission label. A code added in Phase 8
  appears here with no SPA change, and a label can never drift from its code.
- `Par magasin` is a ghost button, Label 12px, rendered **only when the account holds two or more
  magasins**, and only on row hover or row focus. Invisible for every single-magasin business.
- Codes whose fields arrive later (`article.voir_prix_achat` and `vente.voir_marge` in Phase 8,
  `dashboard.voir_ca_global` in Phase 10) are **shown and grantable from Phase 3**; they are part of
  the catalogue (`03-RESEARCH.md` correction 3) and granting one early simply has no visible effect
  yet. Do not hide them, and do not annotate them with a phase number — that is internal vocabulary.

**Default for a new account: every switch off.** Fail-closed, matching `Acces.ANONYME`. A brand-new
account shows a banner at the top of section C:

> Ce compte n'a encore aucun droit. Karim pourra se connecter, mais ne verra rien.

**No presets.** No `Gérant standard` button, no `Tout cocher`, no `Copier les droits de…`. All three are
role tiers wearing a friendly name, and CLAUDE.md #6 forbids them. This is an explicit review item, not
a matter of taste.

### 7.5 Per-magasin override — the only place a grid ever appears

Storage is `(gérant, magasin, permission)` per CLAUDE.md #13. The UI hides that by default:

- **Turning a switch on writes one grant row per granted magasin.** Turning it off deletes them all.
- A row is **uniform** whenever every granted magasin agrees. Uniform is the only state most businesses
  will ever see.

Pressing `Par magasin` expands **that one row** into a sub-list, one switch per granted magasin, inset
`24px`:

```
[ mixte ]  Saisir en caisse                            [ Uniformiser ]
           Personnalisé : 2 magasins sur 3
    [on ]  Anfa
    [on ]  Maârif
    [off]  Californie
```

- The parent switch becomes a **tri-state indicator**: on, off, or mixed. Mixed renders as a dash glyph
  inside the track with `aria-checked="mixed"`, and the helper line becomes
  `Personnalisé : 2 magasins sur 3`.
- Clicking a mixed parent sets **all** magasins on, and the undo toast says so.
- `Uniformiser` collapses the row. If the sub-switches disagree it asks first: title
  `Appliquer le même droit à tous les magasins ?`, body `Les réglages par magasin de « Saisir en
  caisse » seront remplacés. Karim aura ce droit dans les 3 magasins.`, confirm `Uniformiser`.
- **Only rows the owner personalised expand.** The worst case, 21 by N, is reachable only through 21
  deliberate actions and is the owner's own choice. In the expected case, zero rows are expanded.
- A personalised row keeps a `Personnalisé` badge when collapsed, so the state is never hidden.
- Adding a magasin to the account later: uniform rows extend to it automatically, **personalised rows
  do not**. The new magasin starts off and an inline note appears at the top of section C —
  `Californie a été ajouté. Vérifiez les 2 droits personnalisés par magasin.` — anchored to those rows.
  Silently extending a personalised grant would hand out a permission the owner never granted.

### 7.6 Permission prerequisites — the support-cost lever

Several codes are nonsense on their own: `stock.ajuster` without `stock.voir`, `vente.remise` or
`vente.creer` without `vente.voir`, `caisse.saisir` or `caisse.comptage` without `caisse.voir`,
`achat.commander` without `fournisseur.voir`, `ordonnance.saisir` without `ordonnance.voir`,
`client.modifier` without `client.voir`, `vente.voir_marge` without `article.voir_prix_achat`.

**Contract:** a `PREREQUIS` map is declared **server-side** alongside the catalogue and delivered with
it. The UI applies it and explains itself:

- Granting a dependent auto-grants its prerequisites, with an inline note under the row:
  `« Consulter le stock » a été activé automatiquement.`
- Revoking a prerequisite revokes its dependents, with the same kind of note:
  `« Ajuster le stock » a été retiré : il dépend de « Consulter le stock ».`
- One undo toast covers the whole cascade, so `Annuler` restores all of it.
- The prerequisite closure is enforced server-side too. The UI note is an explanation, not the rule.

This removes an entire class of "Karim can't see the stock he's supposed to adjust" calls, which at
2 400 MAD/year per shop is the difference between a viable and an unviable support load.

### 7.7 Who may edit what

| Viewer | Sees | May edit |
|---|---|---|
| Owner, own account | `Propriétaire — accès complet à tous les magasins. Ces droits ne se modifient pas.` | Name, e-mail, own password. **No droits section is rendered at all.** |
| Owner, a gérant | Everything | Everything |
| Gérant with `compte.gerer`, own account | Their droits read-only, switches rendered as static `Oui` / `Non` rows | Only their own password |
| Gérant with `compte.gerer`, another gérant | Everything **inside the intersection of their own droits and magasins** | Cannot grant a droit they do not hold, nor access to a magasin they do not hold — those rows are **absent**, not disabled |
| Gérant with `compte.gerer`, the owner's account | The list row, read-only | Nothing |
| Gérant without `compte.gerer` | The `Paramètres` nav entry is absent; `/parametres/comptes` answers 403 | Nothing |

"Absent, not disabled" applies inside this screen too: a gérant-manager who lacks
`article.voir_prix_achat` does not see that row when editing a colleague. Greying it out would tell them
the permission exists and that they lack it. The server enforces; the UI matches.

### 7.8 Saving, undoing and destroying

**Saving is per toggle and immediate. Section C has no Save button.** Reasons: 21 switches behind one
Save is a form people abandon half-filled, and `JournalDroit` records one actor and timestamp per
grant, which maps exactly to one toggle.

| Interaction | Behaviour |
|---|---|
| Grant a droit | Optimistic switch, PATCH. On failure the switch reverts and a destructive message appears **on that row** — never a toast, which is missed while looking elsewhere. |
| Revoke a droit | Same, plus a toast `Droit retiré : « Saisir en caisse ».` with an **`Annuler`** action for 10 seconds and an explicit close. Undo, not a confirm dialog: 21 switches with confirm dialogs is confirm fatigue, and every one of these is reversible in one click. |
| Grant or remove magasin access | **Confirmation dialog.** Broad blast radius — it changes every droit at once. Removal adds `Les réglages par magasin de 2 droits pour Maârif seront supprimés.` |
| Deactivate an account | **Confirmation dialog**, copy below. |
| Delete an account | **Does not exist, anywhere.** Accounts are referenced by ventes, by `JournalDroit` and by ten years of retention (art. 211 CGI). There is no `Supprimer` in the account UI and the word never appears. |

**The effect-timing line, permanently visible at the foot of section C:**

> Les changements prennent effet immédiatement, dès l'action suivante de l'utilisateur. Il n'a pas
> besoin de se reconnecter.

That one sentence answers the most predictable support question this screen generates, and it is true:
grants are read fresh from the control plane on every request.

### 7.9 Destructive confirmations — exact copy

Two destructive dialogs exist in this phase. Both use shadcn `alert-dialog` with a destructive confirm
button, a secondary button labelled `Retour` (7.10), and **no typed confirmation** — both are
reversible.

**Deactivate an account**

> ### Désactiver le compte de Karim Benali ?
> Il sera déconnecté dès sa prochaine action. Ses ventes et ses saisies restent enregistrées à son nom.
> Vous pourrez réactiver ce compte plus tard.
>
> `[ Retour ]`   `[ Désactiver le compte ]`

**Remove access to a magasin**

> ### Retirer l'accès au magasin Maârif ?
> Karim ne verra plus les clients, le stock, les ventes ni la caisse de Maârif. Les réglages par
> magasin de 2 droits pour ce magasin seront supprimés.
>
> `[ Retour ]`   `[ Retirer l'accès ]`

The second sentence of each states **what survives**. A destructive dialog that names only what is
destroyed leaves the user guessing about their sales history, and guessing is a phone call.

### 7.10 `Annuler` means undo, never cancel

French uses `Annuler` for both "cancel this dialog" and "undo that action". In this product:

- **`Annuler` always means undo**, and appears only as the action on an undo toast.
- A dialog's secondary button is **`Retour`**. A form's escape hatch is **`Fermer`**.
- A cancellable long operation gets **`Interrompre`**.

One rule, three words, no ambiguity across nine future phases.

## 8. Cross-cutting contracts (APP-01, APP-03, PERM-06)

### 8.1 Money — `1 800,00 MAD`, pinned (CLAUDE.md #14, APP-03)

`03-RESEARCH.md` §7 verified that the three plausible locale sources disagree: Django `fr` uses U+00A0,
browser ICU `fr-FR` uses U+202F, and ICU **`fr-MA` uses a full stop** — so the screen would read
`1.800,00 MAD` while the facture reads `1 800,00 MAD`. Reaching for a locale database is the bug.

| Rule | Contract |
|---|---|
| Format | `1 800,00 MAD` — U+00A0 between groups, U+00A0 before `MAD`, decimal comma, always 2 decimals |
| Source of truth | `tests/fixtures/formats_mad.json`, read by **both** pytest and vitest |
| Client implementation | `web/src/format/montant.ts`, a hand-written function. **`Intl.NumberFormat` is forbidden for money**, as is `toLocaleString`, as is any `fr-MA` locale tag anywhere in the SPA |
| Rendering | Right-aligned in tables, `tabular-nums`, never wrapped (the U+00A0 guarantees it) |
| Negative | Leading `-`. Destructive colour **in addition to** the sign, never instead of it |
| Arithmetic | **The SPA never adds two amounts.** Every total it displays (`total_ht`, `total_tva`, `total_ttc`, `reste_a_payer`, `solde_caisse`) is a server field. A serializer that omits a total the UI needs is the bug to fix — not a client-side sum |
| Transport | `COERCE_DECIMAL_TO_STRING = True`; money crosses JSON as a **string** and is parsed to `Number` for display only (CLAUDE.md #7) |
| Audit | `grep -r "fr-MA\|toLocaleString\|Intl.NumberFormat" web/src` must return nothing outside `format/`. Make it a CI line |

**Open, and it is not mine to close:** the U+00A0 group separator is `03-RESEARCH.md` assumption **A1**
and needs a Moroccan optician or the comptable, not more research. It is cheap to change *before* the
fixture is written and expensive after Phase 9's PDFs exist. **Ask, in the same conversation as the
four Phase 6 facturation questions.**

### 8.2 Dates, times and the Casablanca trap

| Rule | Contract |
|---|---|
| Short date | `14/09/2026` — `Intl.DateTimeFormat("fr-FR")`, pinned. Never `fr-MA` (it agrees today and is one ICU update from not) |
| Date and time | `14/09/2026 à 09:14`, 24-hour, `tabular-nums` |
| Long date | `dimanche 14 septembre 2026` — detail headers only, never in a table |
| Storage | `TIME_ZONE = "UTC"` is load-bearing for PgBouncer and **must not** become `Africa/Casablanca` |
| Display | Converted to Africa/Casablanca **in the formatter**, never in settings. Morocco is UTC+1 year-round except a Ramadan shift to UTC+0 — a real off-by-one-day risk on Phase 10's `CA du jour`. Noted now, solved then |
| Input | `type="date"` is not used (its rendering is browser-locale-controlled and shows `mm/dd/yyyy` on an English-locale Windows). A masked text input `jj/mm/aaaa` plus a `popover` calendar. Phase 4 builds it; the decision is made here |

### 8.3 The client-side half of the projection layer (PERM-06)

The server drops a field a gérant may not see. The client must not resurrect it as an empty column, a
dash, a tooltip or a zero.

**Contract:** every table and detail view declares its columns in a registry keyed by the **API field
name**, and the renderer filters to fields actually present in the payload.

```ts
// Declarative: labels, order and alignment stay explicit.
// Presence is data-driven: a field the server omitted cannot render anything at all.
const COLONNES_ARTICLE = [
  { champ: "reference",  libelle: "Référence",      align: "left"  },
  { champ: "designation",libelle: "Désignation",    align: "left"  },
  { champ: "prix_vente", libelle: "Prix de vente",  align: "right", format: "montant" },
  { champ: "prix_achat", libelle: "Prix d'achat",   align: "right", format: "montant" }, // Phase 8
];
// rendu = COLONNES_ARTICLE.filter(c => c.champ in ligne)
```

Consequences, all of which are the point:

- No hardcoded `<th>` anywhere. A header exists only if its data does.
- **No placeholders.** No `—`, no `N/A`, no `0,00 MAD`, no lock icon, no "vous n'avez pas accès à cette
  colonne" tooltip. The column is not there.
- A total derived from an absent field is **not displayed at all**, rather than displayed as zero.
- Detail views follow the same rule via a field registry.
- Phase 3 proves this against a **test-only fixture resource**, not an invented `prix_achat` — the real
  verification is Phase 8's, as `03-RESEARCH.md` correction 3 argues and REQUIREMENTS.md already
  schedules.

**Named client test:** `la colonne absente du payload ne produit aucun en-tête` (vitest), the mirror of
the server's parametrized conformance test.

### 8.4 Print stylesheet — one file now, so Phase 9 is an extension

Phase 3 renders **HTML documents, not PDFs** (`03-RESEARCH.md` correction 4). The SPA ships
`web/src/print.css` from this phase:

- `@page { size: A4; margin: 15mm; }`
- Shell chrome (`sidebar`, top bar, toasts, focus rings) `display: none` on print
- Body 11pt, tables with `thead` repeated via `display: table-header-group`
- Money rendered by the **same formatter** as the screen — this is the whole point of the shared fixture
- `print-color-adjust: exact` on nothing; documents are black on white so a shop's toner budget survives

Phase 9 wraps the same HTML in WeasyPrint and adds branding. It should not need to touch this file's
page setup.

### 8.5 Arabic content inside a French interface

`dir="ltr"` on `<html>`, permanently — there is no Arabic interface (BRAND-04 is Arabic *content*).
But Arabic client names, addresses and shop names must render correctly inside it:

- The font stack carries Arabic faces (§3). Non-negotiable.
- **Every user-supplied name, address or free-text value is wrapped in `<bdi>`.** Without it, an Arabic
  name adjacent to punctuation in a table reorders the surrounding characters and the row reads wrong.
  This is one element in a shared `<Valeur>` component, and it costs nothing.
- Never `text-align` a name column by content direction; keep columns left-aligned so the table stays
  a grid.
- Search must round-trip Arabic input unchanged (§5.5): no stripping, no normalisation client-side.

### 8.6 Global states — specified once, inherited by every later phase

| State | Contract |
|---|---|
| Loading | **Skeletons that match the final layout**, never a full-page spinner, never a layout shift. The content area reserves its height. No artificial minimum delay. A table skeleton renders the real number of columns and 5 rows. |
| Empty | Heading (Heading 18/600) + one explanatory sentence + the primary action. Never an illustration, never "Aucune donnée". Copy per surface in §9. |
| Load error | **Inline card in the content area**, never a toast — a toast for a failed load disappears and leaves a blank screen. Copy: `Impossible de charger les comptes. Vérifiez votre connexion.` plus `[ Réessayer ]`. Never a status code, never English, never a stack trace. |
| Action error | Inline, next to the control that failed (§7.8). |
| 401 | Global handler clears the auth context, stores the attempted path, routes to `/connexion` with `Votre session a expiré. Reconnectez-vous.` Return to the stored path after login. |
| 403 | Full-page: `Vous n'avez pas accès à cette page.` plus `Il vous manque le droit « Consulter la caisse ». Demandez-le au propriétaire.` **Naming the missing droit is deliberate** — the catalogue is identical for every client, so it discloses nothing, and it converts a support call into a self-service request. |
| 404 | `Cette page n'existe pas.` plus a link to the tableau de bord. |
| Connection lost | **Persistent banner under the top bar**, destructive: `Connexion perdue. Vos modifications ne seront pas enregistrées.` Write controls disabled while it is up. This product is **online only and permanently** (CLAUDE.md #1) — competitors advertise offline, so the honest replacement is telling the truth loudly and immediately rather than failing a save silently. |
| Optimistic failure | Revert, then explain in place. Never leave an optimistic state standing after a failed request. |

## 10. Accessibility Contract

Target **WCAG 2.2 AA**. This is a tool someone uses for eight hours a day; the items below are build
requirements, not aspirations.

| Area | Contract |
|---|---|
| Focus | Visible on every focusable element: 2px `#2563EB`, 2px offset. `outline: none` without a replacement is a review failure. Focus order follows visual order; no positive `tabindex`. |
| Focus restoration | Every overlay returns focus to its trigger on close. Every route change moves focus to the `h1` of the new page and announces it politely — otherwise a screen-reader user hears nothing after clicking a nav item. |
| Landmarks | `header`, `nav`, `main`, in that order, one each. Skip link `Aller au contenu` first in the tab order. |
| Forms | Every control has a real `label` (never placeholder-as-label). Errors linked with `aria-describedby` and `aria-invalid`. An error summary at the top of the form receives focus on failed submit. |
| Switches | The visible label is the accessible name. Per-magasin sub-switches get an `aria-label` that includes the magasin: `Saisir en caisse — Anfa`. Mixed parent uses `aria-checked="mixed"`. |
| Tables | Visually hidden `caption`, `scope="col"` on headers, sortable headers are `button`s with `aria-sort`. A row that behaves as a link is focusable and activates on `Enter`. |
| Dialogs | `role="dialog"`, `aria-modal`, labelled by its title, focus to the first control, `Esc` closes, focus returns. Focus trapped **only** here. |
| Announcements | Toasts `aria-live="polite"`; errors `assertive`. Magasin scope change announced politely. |
| Colour | Never the sole carrier of meaning. `Actif` / `Désactivé` carry the word. A negative amount carries the sign. |
| Contrast | 4.5:1 text, 3:1 non-text. Muted text is `#52525B` (7.6:1), never lighter. Verified table in §4. |
| Motion | Nothing over 150ms. `prefers-reduced-motion: reduce` removes all transitions. No auto-playing anything. |
| Timing | Nothing auto-dismisses except the undo toast (10 s), which also has an explicit close and whose action is reversible. WCAG 2.2.1 satisfied by the toast being an enhancement, not the only path. |
| Zoom | Usable at 200% browser zoom. No fixed-height containers that clip text; the shell uses `min-height`, never `height`, on rows and cards. |
| Target size | 44px minimum for icon-only controls, via expanded hit area, not inflated padding (§2). |
| Language | `<html lang="fr">`. Arabic values inside `<bdi>`; if a value's language is known, `lang="ar"` on it. |
