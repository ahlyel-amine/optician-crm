<objective>
Construire l'objet d'acces resolu : la couture que tout le reste du code lit, et la seule
fonction qui lise encore `utilisateur.client` ou `utilisateur.droits`.

Purpose: sans cette couture, chaque module reinvente la question « ce gerant a-t-il le
droit ? », et la reponse derive. Avec elle, le choix cle etrangere contre table
d'appartenance du plan 03-01 redevient reversible, et une tache Celery ou une commande de
gestion peut piloter la projection sans requete HTTP.

Deux proprietes portent tout le reste de la phase :

1. **Fail-closed.** Un acces absent vaut l'ensemble vide, jamais « autoriser ».
   C'est CLAUDE.md #8 applique a la couche de permissions : le contexte de locataire echoue
   ferme, l'acces aussi.
2. **Un seul chemin de code.** L'acces du proprietaire est **materialise** avec le catalogue
   complet et l'ensemble complet des magasins actifs, deliberement, pour que `peut()` n'ait
   aucune branche `if est_proprietaire`. Une branche qui saute la verification pour les
   proprietaires est une branche qu'un bug peut atteindre pour un non-proprietaire.

Output: `Acces`, `acces_pour()`, `AccesMiddleware`, et les tests PERM-04 de resolution au vert.
</objective>

    class Acces:
        utilisateur_id: int | None
        client_id: int | None
        est_proprietaire: bool
        droits_par_magasin: Mapping[int, frozenset[str]]   # magasin_id -> codes

**La divergence assumee avec `03-RESEARCH.md`.** La recherche propose un unique
`permissions: frozenset[str]`. C'est la forme sans dimension magasin que CLAUDE.md #13
interdit. Ici, l'unite de stockage etant `(gerant, magasin, permission)`, l'unite de
resolution l'est aussi.

Trois accesseurs, et leur separation est le coeur de la conception :

- `peut(code, magasin_id=None)` : avec un magasin, le code doit etre dans l'ensemble de ce
  magasin ; **sans** magasin, le code doit etre dans l'ensemble de **tous** les magasins
  accordes. La conjonction est le choix fail-closed : la projection de champs s'applique a
  un serializer entier, pas a une ligne, donc n'autoriser que ce qui est vrai partout evite
  de livrer le prix d'achat du magasin A a un gerant qui ne le detient que dans B.
- `peut_quelque_part(code)` : vrai si le code est detenu dans au moins un magasin. Reserve
  a **deux usages seulement**, et la docstring doit le dire : conditionner une entree de
  navigation, et construire le catalogue pre-intersecte servi a un gerant-gestionnaire. Ce
  n'est **jamais** une autorisation.
- `magasins_pour(code)` : les identifiants de magasins ou le code est detenu. Le plan 03-09
  en a besoin pour repondre « uniforme » ou « personnalise » a l'interface.

`Acces.ANONYME` : tous ensembles vides. `Acces.SCHEMA` : catalogue complet, aucun magasin,
`pour_le_schema=True`, consomme uniquement par le generateur OpenAPI au plan 03-06.

`acces_pour(utilisateur) -> Acces` :

- utilisateur absent, non authentifie, ou `client_id is None` : renvoyer `ANONYME`. Trois
  conditions, une seule sortie.
- proprietaire : **materialiser** `frozenset(Permission.values)` pour chaque magasin actif.
  Pas de branche dans `peut`, la branche est ici, une fois, a la resolution.
- gerant : lire les `AccesMagasin`, **intersecter avec les magasins actifs vivants** de la
  base du client (`Magasin.objects.filter(actif=True, code__in=...)`), puis construire la
  table `magasin_id -> codes` depuis les `DroitAccorde` restreints a ces memes codes de
  magasin. Un octroi nommant un magasin desactive resout vers rien ; les magasins sont
  desactives et jamais supprimes, donc ce cas est normal et non exceptionnel.

Fournir enfin `_PorteurAcces`, objet de cinq lignes portant seulement `.acces` et `.user`,
pour qu'une tache Celery ou une commande de gestion puisse piloter la projection sans
requete HTTP. Le plan 03-06 le consomme.
