<objective>
Complete TENANT-07: several magasins per client business, with stock and caisse scoped to a magasin
inside that client's database.

Purpose: the requirement has two halves. The first is provisioning — `--magasin` repeated on the
operator command seeds every requested magasin, and a client with zero magasins is refused because
it is not a valid state. The second is scoping — the append-only stock and caisse ledgers each carry
a magasin and are queried explicitly through `for_magasin()`.

The design decision that matters here, from `02-RESEARCH.md` section 9: **magasin scoping is
deliberately the opposite of client scoping.** A client is a connection and fails closed; a magasin
is a column and is explicit. There is no magasin contextvar and no implicit default-manager filter,
because cross-magasin reads are legitimate and constant — the owner's dashboard, réappro across
magasins, and possibly one facture série for the whole company. An implicit filter would silently
return partial data to the owner's dashboard: a wrong number with no error, which is worse than a
crash. And CLAUDE.md open question #2 ("is a facture série per magasin legal, or one continuous
série per company?") is unresolved, so the model must not assume either answer.

Output: the scoping convention Phases 5, 6 and 7 inherit, proven against two magasins in one client.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gérant / API caller -> magasin-scoped query | Magasin is a column, not a connection. Nothing in the database layer prevents reading another magasin's rows — the projection is the caller's responsibility, resolved by Phase 3. |
| magasin lifecycle -> fiscal ledger history | Ledger rows reference a magasin. Deleting the magasin must not be able to delete or orphan ten years of retained fiscal records. |
| operator CLI -> magasin codes | Codes are derived from operator-supplied names and become uniqueness keys inside the client database. |
