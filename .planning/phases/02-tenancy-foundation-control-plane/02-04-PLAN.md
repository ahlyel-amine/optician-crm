<objective>
Build provisioning: the `DatabaseProvisioner` interface, the `provision_client` status state machine
with compensating cleanup, the seeding step, and the three operator commands
(`provision_client`, `deprovision_client`, `reap_orphan_databases`) plus the control-plane admin.

Purpose: TENANT-01, TENANT-05 and TENANT-06 are one piece of work with one hard physical constraint.
**`CREATE DATABASE` cannot run inside a transaction block**, so "completes or rolls back cleanly"
cannot be one atomic transaction. It is a status state machine where the control-plane row is the
durable record of intent and the only thing that is transactional — and the invariant that makes
TENANT-05 true is that **only ACTIVE clients are ever routed to or migrated.** A half-provisioned
client is simply not visible to the rest of the system.

TENANT-06 is free if the layering holds: the management command parses arguments and calls
`provision_client(...)`, and the Phase 12 self-serve flow calls the same function from a Celery task.
One code path, two entry points. **The command must contain no provisioning logic of its own** —
that is precisely what the verifier checks.

Output: an operator can onboard a real optician today, and a run killed halfway can be rerun.
</objective>

    db_host=None) -> Client`, following the research algorithm step for step:

      1. **Reserve identity transactionally on `default`.** `transaction.atomic(using="default")`
         + `get_or_create(code=code, defaults=...)`. Return immediately if already ACTIVE. Derive
         `db_name = f"optique_c{client.pk:06d}"` and `db_user = f"optique_u{client.pk:06d}"` —
         **derived from the primary key, never from operator input** (threat T-02-23). Generate the
         password with `secrets.token_urlsafe(32)` only if absent, and store it encrypted. Advance
         to `CREATING_DB`. This is the only atomic step and it is what makes a killed run converge.
      2. **`CREATE ROLE` + `CREATE DATABASE`** through `get_provisioner()`, on the autocommit
         maintenance connection that goes **direct to PostgreSQL**, bypassing PgBouncer.
      3. **`MIGRATING`** — `register_client_database(**client.connection_params())` then
         `call_command("migrate", database=alias_for(client.pk), interactive=False, verbosity=0)`.
         Django's own `django_migrations` table makes this step idempotent for free.
      4. **`SEEDING`** — `with tenant_context(alias): seed_new_client(client, magasins)`.
      5. **Record heads and activate**, transactionally on `default`: `applied_heads`,
         `schema_digest`, `schema_checked_at`, `status = ACTIVE`, `provisioned_at`.
      - `except Exception as exc:` -> `Client.objects.using("default").filter(pk=...).update(
        status=FAILED, last_error=repr(exc)[:2000])` then **re-raise**. Swallowing here would make
        a failure look like a success to the caller.

      Write the per-step idempotency table from the research into the function docstring — it is the
      reason the rerun works and the next reader needs it.

      **Do not implement template databases.** `CREATE DATABASE x TEMPLATE optique_template` turns a
      ~20 s migrate into a ~1 s copy, but no other session may be connected to the template while it
      is copied (so provisioning serialises and fails under concurrency), and a template that drifts
      behind the migration head silently provisions out-of-date clients. Ship `migrate`. Add a
      comment saying templates are a later optimisation, guarded by
      `read_applied_heads(template) == code_heads()`, and only if latency is *measured* to be a
      problem — at manual-onboarding volumes it never will be.

      Also `deprovision_client(client)`: advance to `DROPPING`, `provisioner.drop_database(...)`,
      advance to `DELETED`. Never delete the `Client` row — art. 211 CGI retention and the audit
      trail both want it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator CLI input -> DDL | `--code` and `--raison-sociale` come from a human. They must never reach a `CREATE DATABASE` statement. |
| application -> PostgreSQL maintenance connection | Provisioning holds a role able to `CREATE DATABASE` and `CREATE ROLE` — the most privileged connection in the system, and it goes direct, bypassing PgBouncer. |
| half-provisioned client -> the router | A client whose database exists but is not migrated must not be reachable by any request. |
| reaper -> `pg_database` | A command that drops databases based on a diff is one bad predicate away from destroying a live client. |
