<objective>
Build per-client logical backup and verified single-client restore (TENANT-09), plus the scheduled
Celery Beat fan-out that backs up every active client.

Purpose: the requirement is explicit that per-instance PITR does not satisfy it — *"restoring one
client's logical database alone has been performed and verified — not assumed. Per-instance PITR
that only restores a whole server does not satisfy this, because many client databases share one
instance."* That settles the approach: implement per-client logical backup and restore ourselves,
provider-independent. Two further reasons: a provider feature can only ever be *assumed* to work,
and keeping this provider-independent stops the Phase 1 hosting decision from becoming a hard
dependency of Phase 2.

The word that makes this plan hard is **verified**. Row counts are not verification — they pass
while every column value is wrong. Verification is an ordered per-table `md5` digest folded into one
value, including sequences, compared before and after, with a mutation in between so a no-op
"restore" cannot pass.

Output: a restore drill that has actually been run, with the neighbour proven untouched.
</objective>

      Advance a sequence without inserting a row and assert the digest changes. A restored database
      with reset sequences is **not** identical even when every row matches — and in this product
      that is not academic, because Phase 6's facture numbering depends on counters.

    - `test_tenant09_checksum_is_reproducible_across_session_timezones`
      Compute the digest under two different session `TimeZone` settings and assert they match,

      per session TZ; without pinning it the digest is not reproducible.

      - `SET TIME ZONE 'UTC'` on the connection first, for the reproducibility reason above.
      - For each base table in the `public` schema, ordered by `table_name`:

            SELECT md5(string_agg(row_md5, '' ORDER BY row_md5))
            FROM (SELECT md5(t::text) AS row_md5 FROM <table> t) s;

        Compose the table name with `psycopg.sql.Identifier`, never an f-string.
      - Fold the per-table digests into one `sha256`, then include sequences:
        `SELECT schemaname, sequencename, last_value FROM pg_sequences ORDER BY 1,2`.

           digests non-comparable across platforms.
        2. A column added by a later migration changes every digest, so digests are only comparable
           **within one schema version**. Always record `schema_digest` alongside.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client database -> dump artifact | A `pg_dump` of a client database is a complete copy of that optician's health and commercial data, sitting on a filesystem and then in object storage. Its protection is not the database's protection. |
| restore operation -> live client databases | A restore runs with a role able to create and drop databases, against an instance shared by every client. A wrong target name destroys a different optician's business. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
