<objective>
Build migration fan-out: `manage.py migrate_all [--check] [--parallel N] [--client CODE ...]
[--fail-fast]`, the `MigrationRun` / `MigrationRunResult` records that make a run auditable, and the
two migration-authoring conventions that are painful to retrofit.

Purpose: TENANT-03 has two halves and the second is the one people forget. Applying a migration
everywhere is easy. **Reporting who succeeded, who failed and who is behind — and not letting client
47 failing stop clients 48 through 300 — is the requirement.** So the fan-out uses a *process* pool,
not a thread pool: a process boundary makes failure isolation structurally true rather than
hopefully true. An unhandled exception, a `sys.exit()` from deep inside Django's error handling, or a
corrupted in-memory migration graph cannot escape a child process.

`--check` is the deploy gate: it probes every ACTIVE client, applies nothing, prints a table and
exits 1 if any client is behind.

Output: a deploy can safely fan a schema change across the fleet and an operator can see the result.
</objective>

    function that runs **in a child process**:

      - `django.setup()` first: each child has its own `connections` registry and must build it.
      - Load the `Client` from `default`.
      - `alias = register_client_database(**client.connection_params(direct=True))` —
        **direct to PostgreSQL on 5432, not through PgBouncer.** Migrations run long transactions
        and DDL, which is the opposite of what a transaction pool is for.
      - `before = read_applied_heads(alias)`.
      - If `check_only`: return `{"status": "behind" if pending_plan(alias) else "ok", ...}` and
        apply nothing.
      - Else `call_command("migrate", database=alias, interactive=False, verbosity=0)`, then
        `after = read_applied_heads(alias)`.
      - `except Exception as exc: return {"status": "failed", "error": repr(exc)[:2000], ...}`.
        **Never re-raise.** Put the research's comment in verbatim: *client 47 failing must not stop
        clients 48..300.* This is the single line the requirement turns on.
      - Return a plain dict of primitives only — it crosses a process boundary by pickle, so no
        model instances, no exceptions, no connections.

    `concurrent.futures.ProcessPoolExecutor(max_workers=parallel)`. Default `parallel = 4`; each
    concurrent migration holds one or two connections. DDL locks are per-database, so two `migrate`
    runs against two different databases do not contend (`02-RESEARCH.md` assumption A4 — if that
    turns out wrong the failure mode is slowness, not corruption, and the fix is `--parallel 1`;
    record that in a comment). `fail_fast` is **off by default** and, when on, stops submitting new
    work but still collects results already in flight.

    Persist one `MigrationRunResult` per returned dict, in the parent process, on `default`.

    Register both models in the operator admin with the per-client result table inline, so "who
    failed and why" is one page rather than a log grep.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deploy pipeline -> every client database | One command opens a privileged connection to every client database in sequence. Its blast radius is the entire fleet. |
| child process -> parent process | Fan-out results cross a pickle boundary. Anything non-primitive crossing it is a failure mode, and an exception escaping a child is a fleet-wide abort. |
| data migration -> `default` | An unguarded `RunPython` runs against every alias the router does not veto, including the control plane. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-30 | Denial of Service | One client's migration failure aborting the fleet | mitigate | `migrate_one` runs in a child process and returns a failure dict instead of raising; `--fail-fast` is off by default; `test_tenant03_one_client_failing_does_not_stop_the_others` asserts three result rows exist when the middle client fails. |
| T-02-31 | Tampering | An unguarded `RunPython` data migration writing into the control-plane database | mitigate | `migration_allowed(schema_editor, app_label)` helper plus an AST test over `**/migrations/*.py` that is itself proven to fire against a synthetic unguarded module. |
| T-02-32 | Information Disclosure | `migrate_all` traffic crossing PgBouncer and leaving DDL session state on a pooled server connection | mitigate | `connection_params(direct=True)` — migrations go direct to PostgreSQL on 5432, never through the transaction pooler. Asserted by an acceptance grep. |
| T-02-33 | Tampering | A half-provisioned or suspended client being migrated | mitigate | Only `status=ACTIVE` clients are selected; `test_tenant03_only_active_clients_are_migrated` asserts FAILED and SUSPENDED clients are excluded. |
| T-02-34 | Repudiation | No record of which clients were migrated, when, or why one failed | mitigate | `MigrationRun` plus one `MigrationRunResult` per client with `heads_before`, `heads_after`, duration and error, surfaced in the operator admin. |
| T-02-35 | Denial of Service | Parallel fan-out exhausting the direct PostgreSQL connection limit during a deploy | mitigate | `--parallel` defaults to 4, each holding one to two connections; the budget arithmetic in `02-RESEARCH.md` section 6 accounts for `P` separately from `C_web + C_cel`. |
| T-02-36 | Tampering | A recorded `applied_heads` drifting from reality after a manual `migrate` and being trusted | mitigate | `--check` probes every database and is authoritative; the admin distinguishes "recorded: behind" from "probed: behind"; `schema_checked_at` records when the recorded value was last confirmed. |
</threat_model>
